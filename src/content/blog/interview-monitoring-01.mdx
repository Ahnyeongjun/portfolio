## 관찰성 3요소

**관찰성 (Observability)**: 시스템 내부 상태를 외부에서 얼마나 잘 파악할 수 있는가.

```
Metrics  - 숫자로 표현된 시스템 상태 (응답 시간, 에러율, 요청 수)
Logs     - 이벤트 기록 (무슨 일이 언제 일어났는가)
Traces   - 요청의 전체 흐름 (어느 서비스가 어디서 시간을 썼는가)
```

## Metrics: Prometheus + Grafana

### Prometheus

Pull 방식으로 메트릭을 수집한다. 각 서비스가 `/metrics` 엔드포인트를 노출하면 Prometheus가 주기적으로 가져간다.

```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'spring-app'
    scrape_interval: 15s
    static_configs:
      - targets: ['app:8080']
    metrics_path: '/actuator/prometheus'
```

### Spring Boot Actuator + Micrometer

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus, metrics
  metrics:
    export:
      prometheus:
        enabled: true
```

```gradle
implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-registry-prometheus'
```

`/actuator/prometheus`에서 Prometheus 포맷 메트릭이 나온다.

### 커스텀 메트릭

```java
@Component
public class OrderMetrics {
    private final Counter orderCounter;
    private final Timer orderProcessingTimer;

    public OrderMetrics(MeterRegistry registry) {
        this.orderCounter = Counter.builder("orders.placed")
            .description("주문 생성 수")
            .tag("status", "success")
            .register(registry);

        this.orderProcessingTimer = Timer.builder("orders.processing.time")
            .description("주문 처리 시간")
            .register(registry);
    }

    public void recordOrder() {
        orderCounter.increment();
    }

    public <T> T recordProcessingTime(Supplier<T> action) {
        return orderProcessingTimer.record(action);
    }
}
```

### 주요 메트릭 종류

| 종류 | 설명 | 예시 |
|------|------|------|
| Counter | 단조 증가 (리셋 불가) | 총 요청 수, 에러 수 |
| Gauge | 현재 값 | 현재 연결 수, 메모리 사용량 |
| Timer | 시간 측정 + 분포 | API 응답 시간 |
| Histogram | 값의 분포 | 요청 크기, 응답 크기 |

### Grafana 대시보드

PromQL로 메트릭을 쿼리해 시각화한다.

```
# API 에러율 (5xx 비율)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/
sum(rate(http_server_requests_seconds_count[5m]))

# 99퍼센타일 응답 시간
histogram_quantile(0.99,
  sum(rate(http_server_requests_seconds_bucket[5m])) by (le, uri)
)

# JVM 힙 사용량
jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"}
```

## 메트릭 카디널리티 관리

Prometheus는 **레이블 조합마다 별도의 타임시리즈**를 생성한다. 레이블에 무한히 늘어나는 값(고카디널리티 값)을 넣으면 타임시리즈 수가 폭발적으로 증가한다.

```java
// 위험한 코드: user_id를 레이블로 사용
Counter.builder("api.requests")
    .tag("user_id", userId)      // 사용자 10만 명 = 타임시리즈 10만 개
    .tag("request_id", reqId)    // 요청마다 새 값 = 타임시리즈 무한 증가
    .register(registry);
```

**실제로 발생하는 문제**:

```
타임시리즈 수 = 메트릭 이름 × 레이블 값의 카티전 곱

http_server_requests{method, uri, status}만 있으면
  method(5) × uri(30) × status(5) = 750개

여기에 user_id(100,000)를 추가하면
  750 × 100,000 = 7,500만 개  ← Prometheus 메모리·디스크 폭발
```

카디널리티가 폭발하면 Prometheus 프로세스가 메모리를 전부 소진해 OOMKill되고, 스크레이프 자체가 타임아웃나면서 **정작 봐야 할 정상 메트릭까지 같이 사라진다**. 실무에서는 신규 API에 `user_id`, `request_id`, `email` 같은 레이블을 무심코 추가했다가 배포 몇 분 후 Prometheus가 다운되고 그 시점 이후 전체 메트릭이 결측되는 장애로 나타난다.

**레이블 설계 원칙**:

- 레이블 값의 **가능한 종류 수가 유한하고 작아야 한다** (상태 코드, HTTP 메서드, 서비스 이름 등 - 보통 수십 개 이하)
- 사용자 식별자, 요청 ID, 이메일, 타임스탬프처럼 **값의 종류가 무한한 것은 레이블이 아니라 로그/트레이스로** 보낸다
- 신규 메트릭 추가 시 `count(count by (label_name) (metric_name))`으로 해당 레이블의 카디널리티를 사전에 확인한다

```promql
# 특정 메트릭의 레이블별 카디널리티 확인
count(count by (user_id) (http_server_requests_seconds_count))
```

## Logs: 로깅 전략

### 로그 레벨

```
ERROR - 즉각 대응 필요. 요청 처리 실패, 외부 연동 오류
WARN  - 주의 필요하지만 서비스는 동작. 재시도 성공, 성능 저하
INFO  - 중요한 비즈니스 이벤트. 주문 생성, 사용자 로그인
DEBUG - 개발/디버깅용. 상세 처리 과정
TRACE - 매우 상세. 프레임워크 내부
```

운영 환경: `INFO` 이상.  
개발 환경: `DEBUG` 이상.

### 구조화 로그 (JSON)

```java
// Logback + Logstash Encoder
// 로그가 JSON 형태로 출력됨
log.info("주문 생성 완료",
    kv("orderId", order.getId()),
    kv("userId", order.getUserId()),
    kv("amount", order.getAmount()));
```

```json
{
  "timestamp": "2026-04-02T10:00:00.000Z",
  "level": "INFO",
  "message": "주문 생성 완료",
  "orderId": "12345",
  "userId": "789",
  "amount": 50000,
  "traceId": "abc123",
  "spanId": "def456"
}
```

JSON 로그는 Elasticsearch(ELK Stack)나 CloudWatch Logs에서 필드 기반 검색이 가능하다.

### 로그에 넣으면 안 되는 것

```java
// 절대 금지
log.info("사용자 로그인: password={}", password);        // 비밀번호
log.debug("카드 정보: {}", cardNumber);                  // 결제 정보
log.info("사용자 정보: {}", user.toString());            // 개인정보 전체
```

### 로그 보존/비용 전략

트래픽이 있는 서비스는 로그량이 하루 수십~수백 GB에 이른다. **전량을 영구 보존하면 스토리지 비용이 서비스 운영비를 초과**할 수 있어서, 접근 빈도에 따라 계층을 나눈다.

```
Hot  (0~7일)   - Elasticsearch/OpenSearch, 실시간 검색 가능, 비용 높음
Warm (7~30일)  - 저비용 스토리지 클래스로 이동, 검색은 되지만 느림
Cold (30일~)   - S3/Glacier 등 객체 스토리지로 아카이빙, 규정 준수·사후 조사용
```

```yaml
# ILM (Index Lifecycle Management) 예시 - Elasticsearch/OpenSearch
policy:
  phases:
    hot:
      min_age: "0d"
      actions:
        rollover:
          max_size: "50gb"
          max_age: "1d"
    warm:
      min_age: "7d"
      actions:
        shrink:
          number_of_shards: 1
    delete:
      min_age: "30d"
      actions:
        delete: {}
```

**샘플링**: DEBUG 레벨처럼 볼륨이 큰 로그는 전량 저장 대신 일부만 저장하는 경우도 있다. 단, 에러 로그는 절대 샘플링하지 않는다 - 드물게 발생하는 에러 하나가 샘플링에서 누락되면 장애 원인 파악이 불가능해진다. 볼륨을 줄여야 한다면 DEBUG/TRACE 레벨을 대상으로만 적용한다.

## Traces: 분산 추적

MSA에서 요청이 여러 서비스를 거칠 때 전체 흐름을 추적한다.

```
요청 → API Gateway → 주문서비스 → 결제서비스 → 알림서비스
         10ms           50ms          200ms          30ms
                    ↑ 총 290ms
```

어느 서비스가 느린지 한 눈에 파악할 수 있다.

### OpenTelemetry + Jaeger/Zipkin

```yaml
# application.yml
spring:
  application:
    name: order-service
management:
  tracing:
    sampling:
      probability: 1.0  # 100% 샘플링 (운영에서는 0.1~0.3)
```

```gradle
implementation 'io.micrometer:micrometer-tracing-bridge-otel'
implementation 'io.opentelemetry.instrumentation:opentelemetry-spring-boot-starter'
```

Trace ID가 자동으로 로그에 포함된다. 로그와 트레이스를 연결할 수 있다.

### Head-based vs Tail-based 샘플링

트래픽이 많으면 모든 요청을 100% 트레이싱할 수 없다 (저장 비용, 오버헤드). 어떤 요청을 저장할지 **언제 결정하느냐**에 따라 두 방식으로 나뉜다.

```
Head-based 샘플링
요청 시작
  └─ 그 순간 확률(예: 10%)로 저장 여부를 즉시 결정
  └─ 장점: 구현 간단, 오버헤드 낮음
  └─ 단점: 결정 시점에는 이 요청이 에러가 날지, 느릴지 알 수 없다
            → 정작 중요한 "에러났던 요청", "느렸던 요청"이 90% 확률로 버려짐

Tail-based 샘플링
요청 시작 → 전체 스팬을 일단 버퍼에 모음 → 요청 완료 후 판단
  └─ 에러 발생, 레이턴시 임계치 초과 등 "의미있는" 트레이스만 저장
  └─ 장점: 디버깅에 실제로 필요한 트레이스를 놓치지 않음
  └─ 단점: 완료될 때까지 전체 스팬을 버퍼링해야 해서 메모리·인프라 비용이 크고,
            여러 서비스에 걸친 스팬을 한 곳에 모으는 Collector 계층이 별도로 필요 (예: OTel Collector tail_sampling processor)
```

```yaml
# OpenTelemetry Collector - tail_sampling 예시
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors-policy
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-policy
        type: latency
        latency: { threshold_ms: 1000 }
      - name: baseline-policy
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
```

**실무 판단 기준**: 트래픽이 적거나 비용에 덜 민감하면 head-based 확률 샘플링(예: 10~30%)으로 충분하다. 하지만 **에러율이 낮은 서비스(예: 0.1%)에서 그 에러의 원인을 반드시 트레이스로 확인해야 한다면 head-based로는 대부분 놓친다** - 이때 tail-based가 필요하다. 두 방식을 함께 쓰기도 한다: 베이스라인은 낮은 확률로 head-based 샘플링하고, 에러/느린 요청은 tail-based 정책으로 별도 포획.

## 알람 설계

좋은 알람: **즉각 대응이 필요한 것만** 울린다. 알람이 너무 많으면 알람 피로로 중요한 것을 놓친다.

### 알람 기준

```yaml
# Prometheus Alertmanager
groups:
- name: critical
  rules:
  # 에러율 1% 초과 5분 지속
  - alert: HighErrorRate
    expr: |
      sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
      / sum(rate(http_server_requests_seconds_count[5m])) > 0.01
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "에러율 {{ $value | humanizePercentage }} 초과"

  # 99퍼센타일 응답 시간 2초 초과
  - alert: SlowResponse
    expr: |
      histogram_quantile(0.99,
        sum(rate(http_server_requests_seconds_bucket[5m])) by (le)
      ) > 2
    for: 3m
    labels:
      severity: warning

  # Pod 재시작 감지
  - alert: PodRestarting
    expr: increase(kube_pod_container_status_restarts_total[15m]) > 2
    labels:
      severity: warning
```

### SLO / SLI / SLA

**SLI (Service Level Indicator)**: 측정 지표. "99퍼센타일 응답 시간", "에러율".

**SLO (Service Level Objective)**: 내부 목표. "에러율 < 0.1%", "응답 시간 p99 < 500ms".

**SLA (Service Level Agreement)**: 고객과의 계약. "월 가용성 99.9%".

SLO를 SLA보다 엄격하게 설정해 위반 전에 대응할 시간을 확보한다.

### Multi-Window Multi-Burn-Rate 알람 (Google SRE 방식)

앞서 본 "에러율 1% 초과 5분 지속" 같은 **단순 임계치 알람은 두 가지 문제**가 있다.

```
문제 1. 너무 민감하면 노이즈
  - 5분짜리 짧은 스파이크에도 알람이 울림 → 알람 피로

문제 2. 너무 둔감하면 늦은 감지
  - "1시간 평균 에러율 1% 초과"처럼 긴 윈도우만 보면
    실제로는 이미 30분 전부터 심각하게 터지고 있었는데 알람이 늦게 옴
    → 그 사이 에러버짓(SLO가 허용하는 실패 예산)을 이미 다 태워버림
```

Google SRE는 **에러버짓이 얼마나 빠르게(burn rate) 소진되는지**를 기준으로, **짧은 윈도우와 긴 윈도우를 동시에** 검사해서 이 둘을 절충한다.

```
burn rate = 실제 에러율 / (1 - SLO 목표)

SLO가 99.9%(에러 허용 0.1%)일 때 burn rate 14.4 =
  현재 에러율이 SLO 예산을 720배(30일 예산 ÷ 2일) 속도로 태우는 중
  → 이 속도라면 월간 에러버짓을 2시간 안에 다 쓴다 → 심각(page)

빠른 감지를 위해 짧은 윈도우(5분)로 확인하되,
"5분만 우연히 튄 것"이 아님을 확인하려고 긴 윈도우(1시간)도 같이 걸어야 함을 만족시켜야 알람
```

```yaml
# Prometheus Alertmanager - Multi-Window Multi-Burn-Rate
groups:
- name: slo-burn-rate
  rules:
  # Critical: 짧은 시간에 에러버짓을 급격히 소진 (2시간 내 완전 소진 속도)
  - alert: ErrorBudgetBurnFast
    expr: |
      (
        sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
        / sum(rate(http_server_requests_seconds_count[5m]))
      ) > (14.4 * 0.001)
      and
      (
        sum(rate(http_server_requests_seconds_count{status=~"5.."}[1h]))
        / sum(rate(http_server_requests_seconds_count[1h]))
      ) > (14.4 * 0.001)
    labels:
      severity: page   # 즉시 온콜 호출

  # Warning: 완만하지만 지속적인 소진 (6시간 내 소진 속도)
  - alert: ErrorBudgetBurnSlow
    expr: |
      (
        sum(rate(http_server_requests_seconds_count{status=~"5.."}[30m]))
        / sum(rate(http_server_requests_seconds_count[30m]))
      ) > (6 * 0.001)
      and
      (
        sum(rate(http_server_requests_seconds_count{status=~"5.."}[6h]))
        / sum(rate(http_server_requests_seconds_count[6h]))
      ) > (6 * 0.001)
    labels:
      severity: warning   # 티켓 생성, 다음날 대응 가능
```

짧은 윈도우 조건과 긴 윈도우 조건을 **둘 다 만족**해야 알람이 울리기 때문에, 짧은 스파이크 하나로는 울리지 않고(노이즈 감소), 실제로 지속되는 문제는 긴 윈도우를 기다리지 않고 짧은 윈도우에서 먼저 잡아낸다(빠른 감지). severity를 burn rate 속도별로 나눠서 빠른 소진은 즉시 페이지, 완만한 소진은 다음 근무시간 대응으로 나눈다.

### Prometheus 확장: HA와 장기 저장

단일 Prometheus 인스턴스에는 세 가지 한계가 있다.

```
1. 단일 장애점: Prometheus 파드가 죽으면 그 시간 동안의 메트릭은 영구 손실
2. 로컬 디스크 한계: 기본적으로 로컬 TSDB에 저장 → 보존 기간이 길어질수록 디스크가 커짐
3. 글로벌 뷰 부재: 클러스터/리전마다 Prometheus를 따로 운영하면 "전체"를 한 쿼리로 못 봄
```

**Thanos**로 해결하는 구조:

```
각 클러스터의 Prometheus (로컬, 짧은 보존 기간)
        ↓ sidecar가 블록을 업로드
   Object Storage (S3 등, 장기 저장, 저비용)
        ↓
   Thanos Querier ← 여러 클러스터의 Prometheus + Object Storage를 한 곳에서 쿼리
        ↓
      Grafana (단일 대시보드에서 전체 클러스터 조회)
```

- **Sidecar**: 각 Prometheus 옆에 붙어서 TSDB 블록을 주기적으로 S3 등 객체 스토리지에 업로드
- **Querier**: 여러 Prometheus(sidecar)와 Object Storage를 대상으로 PromQL을 fan-out 쿼리해 하나로 합쳐 응답 → 이 덕분에 Grafana는 Querier 하나만 보면 전체 클러스터를 다 조회 가능
- **Compactor**: Object Storage에 쌓인 블록을 다운샘플링·압축해 장기 보존 비용을 낮춤

같은 문제를 Grafana Mimir나 Cortex도 유사한 구조(수집은 각지에서, 저장·질의는 중앙 객체 스토리지 기반)로 해결한다. 멀티 클러스터를 운영한다면 Prometheus 단독보다 이런 장기 저장·글로벌 뷰 계층이 실무에서는 거의 필수다.

### 온콜과 포스트모템

알람이 울리면 끝이 아니라 **온콜(On-call) 담당자에게 전달되는 흐름**까지 설계해야 한다.

```
Alertmanager → Escalation 정책
  1차: Slack/PagerDuty로 온콜 담당자 호출
  5분 무응답 → 2차 담당자(또는 팀 전체)로 에스컬레이션
  15분 무응답 → 매니저 호출
```

장애 대응이 끝나면 **포스트모템(사후 분석)**을 작성한다. 핵심은 **Blameless(비난 없는)** 원칙이다 - "누가 실수했는가"가 아니라 "어떤 시스템/프로세스의 구멍이 이 실수를 막지 못했는가"를 찾는다. 사람을 탓하면 다음부터 문제를 숨기게 되고, 재발 방지가 오히려 어려워진다.

**알람 피로(Alert Fatigue) 줄이는 실무적 방법**:

- **Runbook 링크 첨부**: 알람에 "무엇을 확인하고 어떻게 조치하는지"로 바로 연결되는 문서 링크를 넣는다. 매번 새로 조사하지 않게 한다.
- **심각도별 채널 분리**: `severity: page`는 온콜 호출, `severity: warning`은 Slack 채널에만 게시하고 티켓으로 처리 - 모든 알람을 같은 채널로 보내면 중요한 것도 묻힌다.
- **자동 조치가 가능한 건 알람 대신 자동화**: 예를 들어 디스크 사용량 임계치 초과 시 알람만 보내는 대신 오래된 로그를 자동 정리하는 스크립트를 먼저 실행하고, 그래도 해결 안 되면 알람.
- **주기적 알람 검토(alert review)**: 최근 N개월간 울린 알람 중 실제로 조치가 필요했던 비율을 확인해, 항상 무시된 알람은 임계치를 조정하거나 제거한다.

## Spring Boot Actuator 엔드포인트

```
/actuator/health          - 헬스 상태 (K8s probe)
/actuator/metrics         - 메트릭 목록
/actuator/prometheus      - Prometheus 포맷 메트릭
/actuator/info            - 애플리케이션 정보
/actuator/loggers         - 런타임 로그 레벨 변경 (재시작 없이)
/actuator/env             - 환경변수 조회
/actuator/threaddump      - 스레드 덤프
/actuator/heapdump        - 힙 덤프
```

운영 환경에서는 `/actuator/health`와 `/actuator/prometheus`만 외부 노출, 나머지는 내부 포트로 제한.

```yaml
management:
  server:
    port: 8081  # 내부 포트
  endpoints:
    web:
      exposure:
        include: health, prometheus
```

## 면접에서 자주 나오는 질문

**Q. 관찰성(Observability) 3요소는?**

Metrics(메트릭), Logs(로그), Traces(분산 추적). 메트릭은 수치로 시스템 상태를 파악하고, 로그는 이벤트 상세를 기록하며, 트레이스는 분산 시스템에서 요청의 전체 흐름을 추적한다.

**Q. 로그 레벨을 어떻게 설정하는가?**

운영에서는 INFO 이상. DEBUG는 너무 많은 로그로 성능에 영향을 준다. Spring Boot Actuator로 재시작 없이 런타임에 특정 패키지 로그 레벨을 변경할 수 있어 장애 상황에서 유용하다.

**Q. 어떤 메트릭을 모니터링하는가?**

골든 시그널 4가지: 레이턴시(응답 시간), 트래픽(요청 수), 에러(에러율), 포화도(자원 사용률). JVM 관련: GC 빈도, 힙 사용률. 비즈니스: 주문 수, 결제 성공률.

**Q. 알람이 너무 많이 울리면 어떻게 하는가?**

임계값을 조정하거나 `for` 조건(지속 시간)을 늘려 일시적 스파이크에 반응하지 않게 한다. 비중요 알람은 severity를 낮추거나 야간에는 묵음 처리한다. 알람을 정기적으로 검토해 실제 대응이 필요했던 것과 아닌 것을 분류한다.

**Q. 메트릭 카디널리티 폭발이 실제로 왜 위험한가?**

Prometheus는 레이블 값의 조합마다 별도의 타임시리즈를 만들고 이걸 메모리에 인덱싱한다. `user_id`처럼 값의 종류가 무한한 레이블을 붙이면 타임시리즈 수가 기하급수적으로 늘어나 메모리를 전부 소진하고, 결국 Prometheus 프로세스가 OOMKill되거나 스크레이프가 타임아웃난다. 문제는 그 여파로 카디널리티를 유발한 메트릭뿐 아니라 **정상적인 다른 메트릭까지 함께 수집이 끊긴다**는 점이다. 그래서 신규 메트릭을 추가할 때는 레이블 값의 종류 수가 유한하고 작은지(수십 개 이하) 사전에 검증해야 한다.

**Q. Multi-window multi-burn-rate 알람이 단순 임계치 알람보다 나은 이유는?**

단순 임계치 알람은 윈도우가 짧으면 일시적 스파이크에도 울려 노이즈가 많고, 윈도우가 길면 실제 장애를 늦게 감지해 그 사이 에러버짓을 과도하게 소진한다. Multi-window 방식은 짧은 윈도우(예: 5분)와 긴 윈도우(예: 1시간)를 **동시에** 만족해야 알람이 울리도록 해서, 짧은 스파이크는 걸러내면서도 실제로 지속되는 문제는 짧은 윈도우에서 먼저 잡아 빠르게 감지한다. 여기에 burn rate(에러버짓 소진 속도)별로 심각도를 나눠서, 빠르게 소진되는 상황은 즉시 페이지하고 완만한 소진은 다음 근무시간에 처리하도록 구분한다.

**Q. 여러 클러스터의 메트릭을 하나로 통합해서 보려면 어떻게 하는가?**

각 클러스터의 Prometheus는 로컬 디스크에 짧은 기간만 보존하고, sidecar가 TSDB 블록을 주기적으로 S3 같은 객체 스토리지에 업로드한다. Thanos Querier가 여러 Prometheus 인스턴스와 객체 스토리지를 대상으로 PromQL을 fan-out 쿼리해 하나로 합쳐 응답하기 때문에, Grafana는 Querier 하나만 바라보면 전체 클러스터의 메트릭을 단일 뷰로 조회할 수 있다. 장기 보존과 비용 절감은 Compactor가 오래된 블록을 다운샘플링·압축해서 처리한다.

**Q. Tail-based 샘플링이 꼭 필요한 상황은 언제인가?**

Head-based 샘플링은 요청이 끝나기 전에 저장 여부를 결정하기 때문에, 에러율이 낮은 서비스(예: 0.1%)에서는 정작 중요한 에러 트레이스가 낮은 확률로 대부분 버려진다. 에러나 느린 요청처럼 "디버깅에 실제로 필요한" 트레이스를 놓치지 않아야 한다면 tail-based가 필요하다. 다만 tail-based는 요청이 끝날 때까지 전체 스팬을 버퍼링해야 해서 Collector 계층에 메모리·인프라 비용이 추가로 든다. 실무에서는 베이스라인은 head-based로 낮게 샘플링하고, 에러/느린 요청만 tail-based 정책으로 별도 포획하는 방식을 함께 쓴다.

**Q. 알람 피로(alert fatigue)를 줄이기 위한 실무적 방법은?**

심각도별로 채널과 대응 경로를 분리한다(`page`는 온콜 호출, `warning`은 채널 게시 후 티켓). 알람에 조치 방법이 담긴 runbook 링크를 첨부해 매번 새로 조사하지 않게 한다. 자동으로 해결 가능한 문제(디스크 정리 등)는 알람 대신 자동 조치 스크립트를 먼저 실행한다. 그리고 주기적으로 알람을 검토해서 실제 대응이 필요했던 비율이 낮은 알람은 임계치를 조정하거나 제거한다.
