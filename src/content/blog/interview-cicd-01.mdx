## Docker 기본 동작 원리

Docker는 Linux 커널의 두 기능을 사용한다.

**namespace**: 프로세스, 네트워크, 파일시스템을 격리한다. 컨테이너가 서로를 볼 수 없는 이유다.

**cgroup**: CPU, 메모리 등 자원 사용량을 제한한다. 컨테이너 하나가 호스트 자원을 전부 먹지 못하게 한다.

VM과 다른 점은 OS 커널을 공유한다는 것이다.

```
VM                          Docker
┌─────────────────┐         ┌─────────────────┐
│ Guest OS (2GB+) │         │  Container       │
│ App             │         │  App             │
├─────────────────┤         ├─────────────────┤
│ Hypervisor      │         │  Docker Engine   │
├─────────────────┤         ├─────────────────┤
│ Host OS         │         │  Host OS (공유) │
└─────────────────┘         └─────────────────┘
```

## 이미지 레이어 구조

Dockerfile의 각 명령어는 레이어를 만든다.

```dockerfile
FROM openjdk:17-slim          # 레이어 1
RUN apt-get install -y curl   # 레이어 2
COPY build/libs/app.jar .     # 레이어 3
CMD ["java", "-jar", "app.jar"]  # 레이어 4
```

변경되지 않은 레이어는 캐시를 재사용한다. **변경 빈도가 낮은 명령어를 위에, 높은 것을 아래에** 써야 빌드가 빠르다.

나쁜 예:

```dockerfile
COPY . .          # 소스 전체 복사 - 파일 하나 바뀌면 이하 전부 캐시 무효화
RUN ./gradlew build
```

좋은 예:

```dockerfile
COPY build.gradle settings.gradle ./   # 의존성 파일만 먼저
COPY gradle/ gradle/
RUN ./gradlew dependencies --no-daemon  # 의존성 캐시

COPY src/ src/                          # 소스는 나중에
RUN ./gradlew build --no-daemon -x test
```

## 멀티스테이지 빌드

빌드 도구와 런타임을 분리해 최종 이미지를 작게 만든다.

```dockerfile
# Stage 1: 빌드
FROM gradle:8-jdk17 AS builder
WORKDIR /app
COPY . .
RUN gradle build --no-daemon -x test

# Stage 2: 실행
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/build/libs/app.jar app.jar

# 보안: root가 아닌 사용자로 실행
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

| 방식 | 이미지 크기 | 빌드 도구 포함 |
|------|------------|--------------|
| 단일 스테이지 (JDK 포함) | ~600MB | O |
| 멀티스테이지 (JRE만) | ~180MB | X |

이미지가 작으면 레지스트리 푸시/풀 속도, 컨테이너 시작 시간 모두 빨라진다.

## 이미지 공급망 보안

이미지를 빌드해서 바로 배포하면 "그 안에 뭐가 들어있는지"를 아무도 검증하지 않은 채 운영에 올라간다. 베이스 이미지의 알려진 CVE, 의존성 패키지의 취약점이 그대로 프로덕션까지 간다.

### 취약점 스캔을 파이프라인 게이트로

```yaml
# .github/workflows/deploy.yml (build-and-push job에 추가)
- name: Build image
  run: docker build -t app:${{ github.sha }} .

- name: Scan with Trivy
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: app:${{ github.sha }}
    severity: CRITICAL,HIGH
    exit-code: '1'          # 취약점 발견 시 파이프라인 실패 → 푸시 자체를 막음
    ignore-unfixed: true    # 패치 안 나온 취약점은 일단 통과 (막을 방법이 없음)
```

`exit-code: '1'`이 핵심이다. 스캔 결과를 로그로만 남기면 아무도 안 본다. 파이프라인을 실패시켜야 "고치기 전엔 배포 못 한다"는 강제력이 생긴다. 다만 HIGH/CRITICAL만 막고 MEDIUM 이하까지 막으면 오탐·패치 지연 때문에 파이프라인이 상시 막히므로 심각도로 선을 긋는다.

### 이미지 서명과 검증 (cosign / Sigstore)

레지스트리에 있는 이미지가 "우리 CI가 실제로 빌드한 그 이미지"인지 보장하는 문제. 레지스트리 접근 권한이 뚫리면 임의로 이미지를 바꿔치기할 수 있는데, 서명이 없으면 K8s는 그걸 구분하지 못한다.

```bash
# CI에서 빌드 후 서명 (키 없이, OIDC 기반 keyless 서명)
cosign sign --yes $ECR_REGISTRY/app@$DIGEST

# 배포 전(또는 admission controller에서) 서명 검증
cosign verify \
  --certificate-identity-regexp "https://github.com/org/repo/.github/workflows/.*" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  $ECR_REGISTRY/app@$DIGEST
```

운영 클러스터에서는 Kyverno나 OPA Gatekeeper 같은 admission controller에 "서명 안 된 이미지는 스케줄링 자체를 거부" 정책을 걸어 강제한다. CI에서 서명만 하고 클러스터가 검증을 안 하면 서명은 장식일 뿐이다.

### SBOM (Software Bill of Materials)

이미지에 어떤 패키지·버전이 들어있는지 목록화한 것. 나중에 특정 라이브러리에서 0-day가 터졌을 때 "우리 서비스 중 어디에 이 패키지가 들어있는가"를 SBOM 없이는 이미지를 하나씩 까봐야 안다.

```bash
syft app:${{ github.sha }} -o cyclonedx-json > sbom.json
```

Log4Shell(2021) 같은 사고에서 SBOM이 있는 조직은 몇 시간 안에 영향받는 서비스를 특정했고, 없는 조직은 며칠씩 전체 이미지를 스캔해야 했다.

### `latest` 태그를 쓰면 안 되는 이유

```
image: app:latest    # 나쁜 예
image: app:v1.2.0     # 그나마 나음
image: app:sha-a1b2c3d  # 권장 - 커밋/빌드 SHA 기반
```

`latest`는 **가변(mutable)** 태그다. 같은 태그가 언제든 다른 이미지를 가리킬 수 있다는 뜻이다.

- 롤백 불가능: "방금 배포한 latest"와 "어제의 latest"를 구분할 방법이 없다.
- 캐시 오염: 노드가 이미지를 캐시하고 있으면 `imagePullPolicy: Always`를 강제하지 않는 한 오래된 캐시가 그대로 쓰인다.
- 재현 불가능: 같은 매니페스트를 다시 apply해도 다른 시점엔 다른 이미지가 뜬다 - IaC의 선언적 특성이 깨진다.

커밋 SHA나 빌드 다이제스트(`app@sha256:...`)를 태그로 쓰면 **불변(immutable)**이라 "이 배포는 정확히 이 이미지"라는 게 항상 보장되고, `kubectl rollout undo`도 정확한 이전 버전으로 돌아간다.

## GitHub Actions 파이프라인

실무에서 실제로 쓴 구조다.

```yaml
# .github/workflows/deploy.yml
name: Build and Deploy

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Cache Gradle
        uses: actions/cache@v4
        with:
          path: ~/.gradle/caches
          key: ${{ runner.os }}-gradle-${{ hashFiles('**/*.gradle*') }}

      - name: Run tests
        run: ./gradlew test

  build-and-push:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Login to ECR
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push image
        env:
          ECR_REGISTRY: ${{ vars.ECR_REGISTRY }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $ECR_REGISTRY/app:$IMAGE_TAG .
          docker push $ECR_REGISTRY/app:$IMAGE_TAG

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to K8s
        run: |
          kubectl set image deployment/app \
            app=$ECR_REGISTRY/app:${{ github.sha }}
          kubectl rollout status deployment/app
```

흐름: `test → build-and-push → deploy`. 앞 단계가 실패하면 다음 단계로 가지 않는다.

## Build-once, Promote-many

환경(dev/staging/prod)마다 이미지를 다시 빌드하는 파이프라인이 흔하지만, 이건 안티패턴이다.

```
나쁜 예:
  dev 배포   → dev용으로 빌드
  staging 배포 → staging용으로 다시 빌드
  prod 배포  → prod용으로 또 다시 빌드
  → 세 이미지가 "같은 소스"인데도 빌드 시점·의존성 캐시가 달라 완전히 동일하지 않을 수 있음
```

```
좋은 예 (Build-once, Promote-many):
  1회 빌드 → app:sha-a1b2c3d 이미지 생성
       ↓ 같은 이미지를 그대로
  dev 환경에 배포 (검증)
       ↓ 같은 이미지를 그대로
  staging 환경에 배포 (검증)
       ↓ 같은 이미지를 그대로
  prod 환경에 배포
```

staging에서 통과한 게 정확히 prod에서 도는 것과 동일한 바이너리라는 게 핵심이다. "staging에서는 됐는데 prod에서 안 된다"는 흔한 사고 원인 중 하나가 바로 환경별로 다시 빌드해서 미묘하게 다른 아티팩트가 배포되는 경우다.

**환경별 차이는 이미지가 아니라 외부 설정으로 주입한다.**

```yaml
# 이미지 안에는 아무 것도 하드코딩하지 않고
# 배포 시점에 ConfigMap/Secret으로 주입
env:
- name: SPRING_PROFILES_ACTIVE
  value: "prod"          # 환경별로 다른 값
envFrom:
- configMapRef:
    name: app-config-prod   # 네임스페이스/환경별로 다른 ConfigMap
```

빌드 시점에 환경변수를 이미지에 굽는(bake) 방식은 Build-once 원칙과 충돌한다. 12-Factor App의 "config는 환경에서 가져온다"는 원칙과 같은 이유다.

## Jenkins vs GitHub Actions

| 항목 | Jenkins | GitHub Actions |
|------|---------|---------------|
| 인프라 | 직접 서버 관리 | GitHub 관리 |
| 설정 | Groovy DSL, 복잡 | YAML, 간단 |
| 플러그인 | 1,800개+ | Marketplace |
| 비용 | 서버 비용 | private 무료 시간 제한 |
| 커스텀 환경 | 자유로움 | self-hosted runner로 가능 |

내부 서버 환경이 필요하거나(보안 정책, VPN), 복잡한 파이프라인 제어가 필요하면 Jenkins. GitHub 기반 프로젝트에서 빠르게 세팅하려면 GitHub Actions.

## GitOps vs Push 기반 CD

앞의 GitHub Actions 예시는 **Push 기반**이다. CI가 테스트·빌드를 마치면 `kubectl set image`로 클러스터에 직접 명령을 밀어넣는다.

```
Push 기반: CI 파이프라인 → (클러스터 접근 권한 필요) → kubectl apply/set image → 클러스터
```

문제는 CI 러너가 프로덕션 클러스터에 대한 쓰기 권한을 항상 들고 있어야 한다는 점이다. CI 파이프라인이 뚫리면 곧바로 클러스터가 뚫린다. 그리고 누군가 `kubectl edit`으로 클러스터를 손으로 고치면(configuration drift) 그 사실을 아무도 모른다 - git에 있는 매니페스트와 클러스터의 실제 상태가 조용히 벌어진다.

**GitOps(Pull 기반)**는 방향을 뒤집는다.

```
GitOps: 클러스터 안의 Argo CD → git 저장소를 주기적으로 감시(pull) → 차이가 있으면 클러스터를 git 상태로 맞춤
```

```yaml
# Argo CD Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
spec:
  source:
    repoURL: https://github.com/org/gitops-repo
    path: apps/my-app
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      selfHeal: true    # 클러스터가 git과 다르면 자동으로 git 상태로 되돌림
      prune: true        # git에서 삭제된 리소스는 클러스터에서도 삭제
```

**왜 더 안전한가**:

1. **접근 권한 역전**: 클러스터 외부(CI)에서 클러스터 안으로 쓰기 권한을 주는 게 아니라, 클러스터 내부 에이전트(Argo CD)가 git을 읽어가는 pull 방식이다. CI는 git에 커밋만 하면 끝 - 클러스터 자격증명을 CI가 들고 있지 않는다.
2. **git이 단일 진실 소스(Single Source of Truth)**: 클러스터의 현재 상태가 궁금하면 클러스터를 볼 필요 없이 git을 보면 된다. 배포 이력도 git log 그대로다.
3. **Drift Detection + selfHeal**: reconciliation loop가 몇 분마다 "git이 원하는 상태" vs "클러스터의 실제 상태"를 diff한다. 누가 `kubectl edit`으로 몰래 고쳐도 다음 sync 주기에 자동으로 원상복구된다. Push 기반에서는 이 drift를 감지할 방법 자체가 없다.
4. **롤백이 곧 git revert**: 문제가 생기면 `git revert` 한 번으로 이전 상태로 되돌린다. 별도의 배포 도구 상태를 신경 쓸 필요가 없다.

## CI 시크릿 관리: 장기 자격증명 대신 OIDC Federation

앞의 파이프라인 예시에서 `Login to ECR` 단계는 실제로는 AWS 자격증명이 필요하다. 가장 쉬운 방법은 Access Key/Secret Key를 GitHub Secrets에 박아두는 것인데, 이게 왜 위험한지가 자주 나오는 꼬리질문이다.

```yaml
# 나쁜 예: 장기 Access Key를 시크릿으로 저장
- uses: aws-actions/configure-aws-credentials@v4
  with:
    aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}       # 유출되면 만료 전까지 계속 유효
    aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
```

문제: 이 키는 **장기(long-lived)**다. 로그에 실수로 찍히거나, 러너가 침해당하거나, Secrets 설정을 잘못 건드리면 누출된 키가 회수되기 전까지 무기한 유효하다.

```yaml
# 좋은 예: OIDC로 임시 자격증명만 발급받음
permissions:
  id-token: write   # GitHub가 OIDC 토큰을 발급할 수 있게 허용

steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789:role/github-actions-deploy
      aws-region: ap-northeast-2
      # access key 없음 - GitHub의 OIDC 토큰으로 IAM Role을 assume해서
      # 이 워크플로우 실행(job) 동안만 유효한 임시 자격증명(보통 1시간)을 받음
```

IAM Role의 Trust Policy에서 "이 GitHub 저장소의 이 워크플로우에서만 assume 가능"하도록 `sub` 클레임을 제한한다.

```json
{
  "Effect": "Allow",
  "Principal": {"Federated": "arn:aws:iam::123456789:oidc-provider/token.actions.githubusercontent.com"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:sub": "repo:org/repo:ref:refs/heads/main"
    }
  }
}
```

**핵심 차이**: 저장된 비밀 자체가 없다(Secretless). 탈취할 대상이 없으니 유출 위험이 근본적으로 줄고, 설령 토큰이 새더라도 짧은 유효시간과 저장소/브랜치 제한 때문에 피해 범위가 극히 제한된다.

## 무중단 배포 전략

### Rolling Update

기존 파드를 하나씩 새 버전으로 교체한다.

```yaml
# K8s Deployment
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 최대 1개 추가 파드
      maxUnavailable: 0  # 항상 desired 수 유지
```

장점: 추가 인프라 불필요.  
단점: 배포 중 구버전/신버전이 동시에 존재한다. API가 호환되지 않으면 문제가 생긴다.

### Blue-Green

구버전(Blue)을 유지한 채 신버전(Green)을 별도로 띄운 후, 트래픽을 한 번에 전환한다.

```
사용자 → Load Balancer
              ↓
    [Blue: v1]  [Green: v2]  ← 검증 후 전환
```

장점: 즉시 롤백 가능(트래픽만 다시 Blue로).  
단점: 인프라가 2배 필요한 순간이 있다.

### Canary

트래픽 일부만 신버전으로 보내고, 문제 없으면 점진적으로 늘린다.

```yaml
# K8s + Ingress 예시
nginx.ingress.kubernetes.io/canary: "true"
nginx.ingress.kubernetes.io/canary-weight: "10"  # 10%만 신버전으로
```

장점: 실제 트래픽으로 신버전 검증 가능.  
단점: 설정이 복잡하다. Istio나 Argo Rollouts 같은 도구가 필요할 수 있다.

### 자동 롤백: 메트릭 기반 판단

위 nginx canary-weight 예시는 트래픽 비율만 조절할 뿐, "문제가 있는지"는 사람이 대시보드를 보고 판단해서 다음 단계로 넘기거나 되돌려야 한다. 새벽에 배포했는데 사람이 안 보고 있으면 카나리가 10%에서 방치된 채로 있거나, 문제를 늦게 발견한다.

**Argo Rollouts**는 카나리 각 단계 사이에 자동으로 메트릭을 검사하는 `AnalysisTemplate`을 끼워넣는다.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: {duration: 5m}
      - analysis:
          templates:
          - templateName: success-rate-check   # 아래 AnalysisTemplate 참조
      - setWeight: 50
      - pause: {duration: 5m}
      - setWeight: 100
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate-check
spec:
  metrics:
  - name: error-rate
    interval: 1m
    successCondition: result < 0.01     # 에러율 1% 미만이어야 통과
    failureLimit: 2                      # 2번 연속 실패하면 자동 롤백
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{status=~"5..",version="canary"}[2m]))
          / sum(rate(http_requests_total{version="canary"}[2m]))
```

`setWeight: 10`으로 신버전에 트래픽 10%를 보내고, 5분간 Prometheus에서 신버전의 에러율을 실시간으로 조회한다. 조건을 2번 연속 충족 못 하면 **사람 개입 없이** 즉시 이전 버전으로 롤백한다. 통과하면 다음 단계(50% → 100%)로 자동 진행한다.

사람이 수동으로 트래픽을 옮기는 방식과의 차이는 **반응 속도와 일관성**이다. 사람은 대시보드를 계속 보고 있어야 하고, 판단 기준이 그때그때 다를 수 있다. AnalysisTemplate은 "에러율 1% 미만"이라는 기준을 코드로 고정해두고, 새벽 배포든 낮 배포든 동일하게 즉시 판단한다.

## K8s 핵심 오브젝트 관계

```
Deployment
└── ReplicaSet
    └── Pod (컨테이너 실행 단위)

Service (Pod 그룹에 안정적인 엔드포인트 제공)
└── Pod 선택: label selector

Ingress (외부 HTTP 트래픽 → Service 라우팅)
└── Service
```

```yaml
# Deployment
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-service
  template:
    metadata:
      labels:
        app: my-service
    spec:
      containers:
      - name: app
        image: my-image:v2
        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
        readinessProbe:
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
```

`readinessProbe`가 없으면 컨테이너가 시작되자마자 트래픽을 받는다. Spring Boot는 애플리케이션이 뜨는 데 몇 초가 걸리기 때문에 준비 완료 전에 요청이 들어오면 에러가 난다.

## Docker Compose - 로컬 개발 환경

```yaml
# docker-compose.yml
services:
  app:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/mydb
      SPRING_REDIS_HOST: redis
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: mydb
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d mydb"]
      interval: 5s
      timeout: 5s
      retries: 5
    volumes:
      - postgres_data:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru

volumes:
  postgres_data:
```

`depends_on`만 쓰면 컨테이너 시작 순서만 보장하고 서비스 준비는 보장하지 않는다. `condition: service_healthy`와 `healthcheck`를 같이 써야 DB가 실제로 준비됐을 때 앱이 시작된다.

## 실무에서 도입한 CI/CD 개선

기존에는 수동 배포였다. 개발자가 직접 서버에 SSH 접속해서 jar를 올렸다.

문제:

- 배포 중 서비스가 잠깐 끊겼다
- 누가 언제 뭘 배포했는지 기록이 없었다
- 실수로 테스트 통과 안 된 코드가 올라간 적이 있었다

개선:

1. **GitHub Actions**: PR merge → 자동 테스트 → Docker 이미지 빌드 → 레지스트리 푸시
2. **K8s Rolling Update**: `maxUnavailable: 0`으로 서비스 중단 없이 교체
3. **Rollout 검증**: `kubectl rollout status` 명령으로 파이프라인에서 배포 성공 여부 확인
4. **Slack 알림**: 배포 성공/실패 결과를 채널로 발송

결과: 배포 시간 15분 → 3분, 배포 중 에러율 0%

## DB 마이그레이션과 무중단 배포의 충돌: Expand-Contract

Rolling Update 중에는 구버전과 신버전 파드가 동시에 떠 있는 시간이 있다. 이 상태에서 신버전이 요구하는 스키마 변경을 한 번에 적용하면, 아직 살아있는 구버전이 깨진다.

예를 들어 `users` 테이블의 컬럼명을 `email` → `email_address`로 바꾸는 상황.

```sql
-- 절대 하면 안 되는 방식: 한 번에 rename
ALTER TABLE users RENAME COLUMN email TO email_address;
-- → 배포 도중 살아있는 구버전 코드는 여전히 SELECT email ... 을 실행 중
-- → 컬럼이 없다는 에러로 즉시 장애
```

**Expand-Contract 패턴**은 하나의 변경을 여러 배포에 걸쳐 나눠서, 매 순간 구버전과 신버전 둘 다 정상 동작하게 만든다.

```sql
-- 1단계 (Expand) - 새 컬럼 추가, 기존 컬럼은 그대로 둠
ALTER TABLE users ADD COLUMN email_address VARCHAR(255);
```
```java
// 이 시점에 배포하는 신버전: 양쪽에 다 쓰기 (dual write)
user.setEmail(email);            // 구버전 호환용
user.setEmailAddress(email);     // 신규 컬럼
```

```sql
-- 2단계 (Backfill) - 기존 데이터를 새 컬럼으로 채움 (배치, 트래픽 적은 시간대)
UPDATE users SET email_address = email WHERE email_address IS NULL;
```

```java
// 3단계 - 읽기를 신규 컬럼으로 전환 (이 배포부터 email 컬럼은 안 씀)
String email = user.getEmailAddress();
```

```sql
-- 4단계 (Contract) - 아무도 안 쓰는 게 확인되면 구컬럼 삭제
ALTER TABLE users DROP COLUMN email;
```

**핵심 규칙**: 각 단계는 독립적으로 배포 가능해야 하고, 그 상태로 구버전이 얼마간 계속 떠 있어도 문제가 없어야 한다. "컬럼 추가"와 "코드가 그 컬럼을 요구"하는 배포를 분리하는 게 이 패턴의 본질이다 - 스키마 변경이 먼저 나가서 안전하게 존재한 다음에, 코드가 그걸 쓰기 시작한다.

컬럼 삭제·타입 변경·NOT NULL 제약 추가처럼 "되돌릴 수 없거나 구버전을 깨뜨리는" 모든 마이그레이션에 같은 원칙이 적용된다.

## 면접에서 자주 나오는 질문

**Q. Docker와 VM의 차이는?**

VM은 OS를 통째로 가상화해 커널을 격리한다. Docker는 호스트 커널을 공유하고 namespace/cgroup으로 프로세스를 격리한다. VM은 무겁고 완전히 격리되며, Docker는 가볍고 빠르지만 커널을 공유한다.

**Q. 이미지 레이어 캐시를 잘 활용하려면?**

자주 변경되는 파일(소스 코드)은 Dockerfile 아래에, 잘 안 바뀌는 것(의존성 설치)은 위에 둔다. 소스 코드만 바뀌면 의존성 레이어는 캐시에서 재사용된다.

**Q. Rolling Update 중 구버전/신버전이 동시에 뜨면 어떤 문제가 생기는가?**

API 하위 호환성이 없으면 문제다. 예를 들어 DB 컬럼을 삭제하는 마이그레이션을 신버전에서 먼저 실행하면, 아직 떠있는 구버전이 해당 컬럼을 참조해서 에러가 난다. 이런 경우 Blue-Green이나, 마이그레이션을 expand-contract 패턴으로 여러 배포에 걸쳐 나눠 진행한다.

**Q. readinessProbe와 livenessProbe의 차이는?**

- `readinessProbe`: 트래픽을 받을 준비가 됐는지. 실패하면 해당 파드는 Service 엔드포인트에서 제외된다.
- `livenessProbe`: 컨테이너가 살아있는지. 실패하면 컨테이너를 재시작한다.

Spring Boot 앱은 두 가지 다 `actuator/health`를 쓰되, readiness는 외부 의존성(DB, Redis) 포함, liveness는 앱 프로세스만 체크하도록 분리하면 더 정밀하다.

**Q. 이미지 태그를 `latest`로 쓰면 왜 위험한가?**

`latest`는 가변 태그라 같은 이름이 시점마다 다른 이미지를 가리킬 수 있다. 롤백 시 "정확히 어떤 이미지로 돌아가야 하는가"를 특정할 수 없고, `imagePullPolicy`를 `Always`로 강제하지 않으면 노드 캐시 때문에 배포했는데도 실제로는 이전 이미지가 그대로 뜨는 경우도 생긴다. 커밋 SHA나 이미지 다이제스트 기반의 불변 태그를 쓰면 "이 배포 = 이 이미지"가 항상 1:1로 보장된다.

**Q. 빌드 캐시가 무효화되는 시점을 예상하지 못해 빌드가 느려질 때, 원인을 어떻게 짚는가?**

Docker의 레이어 캐시는 이전 레이어까지 동일해야 이어서 재사용된다. `COPY . .`처럼 소스 전체를 앞쪽에서 복사하면 파일 하나만 바뀌어도 그 레이어부터 전부 무효화된다. `.dockerignore`에 불필요한 파일(로그, `.git`, 빌드 산출물)이 빠져 있어 매번 컨텍스트가 달라지는 경우도 흔한 원인이다. `docker build --progress=plain`으로 어느 레이어부터 캐시 미스가 나는지 직접 확인하고, 자주 바뀌는 파일을 Dockerfile 아래로, 안 바뀌는 의존성 설치를 위로 재배치해서 해결한다.

**Q. Argo Rollouts와 순수 K8s Deployment의 RollingUpdate는 어떻게 다른가?**

RollingUpdate는 `maxSurge`/`maxUnavailable`만으로 정해진 순서를 무조건 진행한다 - 중간에 문제가 있는지 스스로 판단하지 않는다. Argo Rollouts는 `Rollout`이라는 커스텀 리소스로 카나리 단계별 트래픽 비율, 대기 시간, 그리고 `AnalysisTemplate`로 각 단계마다 실시간 메트릭 검사를 끼워넣는다. 즉 RollingUpdate는 "정해진 각본대로 진행"이고, Argo Rollouts는 "매 단계 메트릭으로 통과/롤백을 판단하며 진행"이라는 차이다.

**Q. 카나리 배포 중 에러율이 튀면 자동으로 롤백되게 하려면 무엇이 필요한가?**

세 가지가 맞물려야 한다. 첫째, 카나리 버전과 안정 버전의 메트릭을 라벨(`version=canary`)로 구분해서 수집하는 모니터링(Prometheus). 둘째, "에러율 1% 미만" 같은 판단 기준을 코드로 정의한 분석 정책(Argo Rollouts의 `AnalysisTemplate`). 셋째, 그 판단을 실행하고 실패 시 즉시 되돌릴 수 있는 오케스트레이션(Rollout controller). 사람이 대시보드를 계속 지켜보는 방식은 반응이 늦고 새벽 배포에는 아예 무방비다.

**Q. GitOps 환경에서 시크릿은 어떻게 관리하는가?**

git 저장소는 평문 시크릿을 절대 담으면 안 되는데, GitOps는 "git이 원본"이라는 전제와 충돌하는 것처럼 보인다. 실무에서는 세 가지 방식을 쓴다. **SOPS**는 파일을 KMS/PGP 키로 암호화한 채로 git에 커밋하고, 클러스터의 컨트롤러가 복호화한다. **Sealed Secrets**는 클러스터 안의 컨트롤러만 복호화 가능한 방식으로 암호화해 커밋하는 방식으로 SOPS와 유사한 목적이다. **External Secrets Operator**는 git에는 "시크릿이 어디 있는지에 대한 참조"만 커밋하고 실제 값은 AWS Secrets Manager나 Vault 같은 외부 저장소에 두며, 컨트롤러가 클러스터 기동 시 그 값을 가져와 K8s Secret으로 동기화한다. 실무에서는 외부 시크릿 저장소와의 단일 진실 소스 분리가 명확한 External Secrets Operator 방식을 가장 많이 쓴다.
