## 왜 "템플릿 도구"라는 설명이 반쪽짜리인가

Helm을 소개할 때 제일 흔한 설명이 "반복되는 YAML을 템플릿화해서 값만 바꿔 재사용하는 도구"다. 틀린 말은 아니지만, 그게 Helm을 쓰는 이유의 절반밖에 안 된다. 나머지 절반은 **배포 이력을 버전으로 관리하고, 그 버전으로 되돌릴 수 있다는 것**이다. 템플릿 엔진 역할만 본다면 Kustomize로도 충분한 경우가 많은데, Helm이 따로 존재하는 이유는 정확히 이 **릴리스(Release) 개념** 때문이다.

## 1. Chart, Release, Revision - 세 층위를 구분한다

Helm을 정확히 이해하려면 세 단어를 헷갈리지 않아야 한다.

| 개념 | 정의 | 비유 |
|---|---|---|
| **Chart** | 애플리케이션을 배포하는 방법이 정의된 템플릿 패키지(버전 관리되는 소스) | 클래스(class) |
| **Release** | 그 Chart를 실제 클러스터의 특정 네임스페이스에 설치한 "인스턴스" | 그 클래스로 만든 객체(instance) |
| **Revision** | 하나의 Release가 `upgrade`될 때마다 쌓이는 버전 번호 (1, 2, 3, ...) | 그 객체의 변경 이력(git commit 하나하나) |

같은 Chart를 같은 클러스터에 `helm install my-app`, `helm install my-app-staging` 두 번 설치하면 Release가 두 개 생긴다 - Chart는 하나지만 Release는 독립적인 두 개다. 그리고 `my-app` Release를 `helm upgrade`로 세 번 업그레이드하면, Revision이 1→2→3→4로 쌓인다.

## 2. Revision은 실제로 어디에 저장되는가

`helm history my-app`을 실행하면 지난 업그레이드 목록이 나오는데, 이 이력이 **클러스터 안의 Secret(또는 구버전은 ConfigMap) 오브젝트**로 저장된다는 걸 아는 사람은 생각보다 적다.

```bash
kubectl get secrets -n <namespace> -l owner=helm
# sh.helm.release.v1.my-app.v1
# sh.helm.release.v1.my-app.v2
# sh.helm.release.v1.my-app.v3   ← 가장 최근 Revision
```

각 Secret의 데이터에는 **그 Revision 시점에 실제로 클러스터에 적용됐던 완전한 렌더링 결과(매니페스트 전체)** 가 gzip 압축 + base64 인코딩되어 그대로 들어있다. 즉 Helm은 "이번에 뭘 바꿀지"만 기억하는 게 아니라, **매 Revision마다 그 시점의 완성된 상태 전체를 스냅샷으로 통째로 저장**해둔다.

## 3. `helm rollback`이 실제로 하는 일

`helm rollback my-app 2`를 실행하면 Helm이 하는 일은 이렇다.

1. `sh.helm.release.v1.my-app.v2` Secret을 읽어서, Revision 2 시점에 저장해둔 완전한 매니페스트를 꺼낸다.
2. 그 매니페스트를 지금 클러스터에 그대로 다시 적용(apply)한다.
3. 이 롤백 자체도 새로운 Revision(예: v5)으로 기록된다 - "되돌렸다"는 사실 자체도 이력에 남는다.

여기서 중요한 포인트: **롤백은 Chart 소스로 다시 렌더링하는 게 아니라, 과거에 이미 렌더링된 결과물을 그대로 재생하는 것**이다. 그래서 롤백 시점에 Chart 저장소(Git)에 있는 파일이 바뀌었든 말든 상관없이, **그 Revision이 실제로 클러스터에 적용됐던 그 상태 그대로** 정확히 복원된다. Kustomize나 순수 `kubectl apply -f`로는 이 "과거 렌더링 결과의 스냅샷"이 자동으로 남지 않기 때문에, 되돌리려면 Git에서 해당 커밋의 YAML을 다시 apply해야 하고 그 사이 참조하던 다른 리소스가 바뀌어 있으면 결과가 100% 같지 않을 수 있다.

## 4. GitOps(ArgoCD)와 같이 쓸 때는 무엇이 달라지는가

ArgoCD 같은 GitOps 툴은 "Git의 선언 상태 = 진실의 원천"이라는 철학이라, 롤백도 원칙적으로는 **Git에서 이전 커밋으로 되돌리고 그 상태를 다시 동기화**하는 방식을 권장한다. Helm의 Revision 롤백과는 철학이 약간 다르다 - Helm은 "클러스터 안에 저장된 과거 스냅샷"을 신뢰하고, GitOps는 "Git 저장소에 있는 선언"을 신뢰한다.

ArgoCD에서 Helm Chart를 배포 대상으로 쓸 경우, 실무적으로는 두 이력이 같이 존재한다 - **Git 커밋 이력**(어떤 값·템플릿이 언제 바뀌었는지)과 **Helm Revision 이력**(그게 실제로 클러스터에 언제 적용됐는지, 정확히 어떤 렌더링 결과였는지). 배포 드리프트를 조사할 때는 두 이력을 같이 봐야 "선언은 이렇게 바뀌었는데 실제로는 언제 적용됐는가"가 정확히 맞춰진다.

## 5. 정리 - 템플릿 엔진 + 릴리스 버전 관리자

| 역할 | 담당 개념 | 대체 가능한 도구 |
|---|---|---|
| 반복 YAML을 값으로 치환 | Chart의 templates/values.yaml | Kustomize로도 어느 정도 대체 가능 |
| 배포 인스턴스 식별 | Release | (Kustomize엔 이 개념이 없음) |
| 버전별 완전한 스냅샷 저장·롤백 | Revision(클러스터 내 Secret) | (Kustomize·순수 kubectl엔 이 개념이 없음) |

"Helm을 쓰는 이유"를 한 줄로 압축하면, **템플릿 재사용은 덤이고 진짜 이유는 "배포된 상태를 버전으로 관리하고 그 버전으로 정확히 되돌릴 수 있다는 것"**이다.

## 체크리스트

- [ ] Chart·Release·Revision 세 개념을 각각 정확히 구분해서 설명할 수 있는가
- [ ] Revision 이력이 클러스터 안 Secret에 완전한 매니페스트 스냅샷으로 저장된다는 것을 아는가
- [ ] `helm rollback`이 Chart를 다시 렌더링하는 게 아니라 과거 렌더링 결과를 그대로 재생한다는 차이를 설명할 수 있는가
- [ ] Helm Revision 이력과 GitOps(Git 커밋 이력)가 서로 다른 신뢰 원천이라는 것을 설명할 수 있는가
