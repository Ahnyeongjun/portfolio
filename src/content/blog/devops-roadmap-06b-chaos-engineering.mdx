## 목표

[Prometheus·Loki·OpenTelemetry로 세운 관측 스택](/blog/devops-roadmap-06-observability-chaos)이 "설치되어 있다"는 것과 "실제 장애를 탐지한다"는 것은 다른 주장이다. 이 편은 그 스택에 실제로 장애를 주입해서, 알림이 오는지·얼마나 걸리는지·애초에 그 장애 유형을 잡을 수 있는 규칙이었는지를 직접 검증한다.

## 개념: 카오스 엔지니어링과 정상 상태 가설

카오스 엔지니어링은 "장애가 언젠가 난다"는 걸 전제로, 실제로 터지기 전에 통제된 환경에서 미리 장애를 일으켜보고 시스템과 사람(알림·대응 절차)이 제대로 반응하는지 검증하는 방법론이다. 원전(Netflix의 Chaos Monkey)에서 나온 정의를 이 랩 규모로 옮기면 핵심은 하나로 압축된다 - **정상 상태 가설(steady state hypothesis)을 먼저 정의하고, 그 가설이 장애 상황에서도 유지되는지를 실험으로 반증(falsify)한다.**

```
정상 상태 가설의 예:
  "api-server의 5xx 비율은 5% 미만이다"
  "RabbitMQ에 발행된 메시지는 워커가 반드시 ack/nack 처리한다"
  "노드 하나가 죽어도 파드는 5분 안에 다른 노드로 재스케줄된다"

실험 = 이 가설을 깨뜨릴 조건을 의도적으로 만들고, 실제로 깨지는지 관찰
```

이 틀에서 보면 실험의 목적은 "장애를 일으키는 것"이 아니라 **"장애가 났을 때 탐지까지 얼마나 걸리는지, 그리고 정상 상태 가설이 실제로 방어되는지를 미리 재보는 것"**이다. 이 시리즈의 모든 실험은 그 시간을 재는 게 진짜 목적이고, 주입 규모(blast radius)를 랩 클러스터 전체가 아니라 노드 1대·파드 1개 단위로 좁혀서 진행한 것도 "실서비스였다면 영향 범위를 최소화해야 한다"는 원칙을 그대로 반영한 것이다.

각 실험은 **가설 정의 → 주입 → 관측 → 기록**의 순서로 진행하고, 주입 시작 시각을 먼저 기록해야 나중에 "알림까지 걸린 시간"을 정확히 잴 수 있다.

## 실험 설계: 4종

### 노드 다운

```bash
# 실험 대상 워커 노드에서
sudo systemctl stop kubelet
# 또는 VM 자체를 강제 종료

# 관측할 것
# - kubectl get nodes 에서 NotReady로 바뀌는 시점
# - 해당 노드의 파드가 다른 노드로 재스케줄되기까지 걸리는 시간 (기본 pod-eviction-timeout 5분)
# - Alertmanager 알림이 Discord에 도착하는 시점
```

kubelet이 멎으면 컨트롤플레인은 일정 시간(`node-monitor-grace-period`, 기본 40초) 동안 하트비트가 없는 노드를 `NotReady`로 표시하고, 그 뒤로도 `pod-eviction-timeout`(기본 5분)이 지나야 비로소 그 노드의 파드를 다른 곳으로 재스케줄한다. 즉 "노드가 죽었다"와 "서비스가 실제로 복구된다" 사이에는 기본값만으로도 5분 이상의 구조적 지연이 있다는 뜻이고, 이 수치 자체가 나중에 SLO를 잡을 때([07편](/blog/devops-roadmap-07-sli-slo-error-budget)) 참고할 하한선이 된다.

### OOMKill

리눅스 커널은 메모리가 부족해지면 임의로 프로세스를 골라 강제 종료해서 시스템 전체가 멎는 걸 막는다 - 이 메커니즘을 OOM(Out Of Memory) Killer라 부른다. 컨테이너에 메모리 `limits`를 걸어두면, 그 컨테이너가 한도를 넘었을 때 커널이 호스트 전체 대신 그 컨테이너만 골라 종료한다(OOMKilled).

```yaml
# 의도적으로 낮은 메모리 제한을 건 테스트 파드
resources:
  limits: {memory: "64Mi"}
```
```bash
kubectl run oom-test --image=polinux/stress --limits=memory=64Mi -- \
  stress --vm 1 --vm-bytes 256M
# kubectl describe pod oom-test 에서 OOMKilled 상태 확인
# Prometheus의 container_oom_events_total 메트릭에 반영되는 시점 확인
```

### 디스크 풀

```bash
# 워커 노드에서 디스크를 의도적으로 채움
fallocate -l 10G /tmp/fillfile
# kubelet의 disk pressure 감지 → 노드가 파드 축출(evict)을 시작하는지 확인
# node-exporter의 node_filesystem_avail_bytes 알림이 임계치를 넘는 시점 확인
```

### RabbitMQ 강제 종료

```bash
kubectl delete pod rabbitmq-0 --grace-period=0 --force
# ack/nack 파이프라인이 이 상황에서 실제로 메시지를 보존하는지 재검증
```

메시지 브로커 자체를 즉시 종료(`--grace-period=0`)하는 건 "정상 종료(graceful shutdown)를 건너뛴다"는 의미다 - 브로커가 처리 중이던 메시지를 디스크에 flush할 기회조차 주지 않고 죽이는 최악의 경로를 재현해서, ack되지 않은 메시지가 재큐잉되는지, 컨슈머가 재연결에 성공하는지를 확인한다.

## 실제로 실행한 결과

| # | 실험 | 탐지 시간 | 비고 |
|---|------|-----------|------|
| 1 | RabbitMQ 파드 강제삭제 | 알림 없음 (46초 내 자기치유) | worker 재연결 로직이 임계치 도달 전에 정상 동작 - 이것도 유효한 결과다 |
| 2 | OOMKill | kubectl 기준 9초, **메트릭 알림은 못 잡음** | `container_oom_events_total`이 재시작 없이 죽는 파드는 못 잡는다는 한계 발견 → `kube_pod_container_status_last_terminated_reason` 기반 규칙으로 교체 |
| 3 | 노드 다운(kubelet 중지) | 약 2분(NotReady) | IP 착각으로 의도와 다른 노드에 주입했지만, 조기 발견 후 3분 만에 복구(축출 타임아웃 전이라 서비스 영향 없음) |
| 4 | 디스크 풀 | 13초(DiskPressure) | kubelet의 자동 image GC가 축출 전에 스스로 ~5GB를 회수하는 것까지 실측 확인 |

4개 전부 디스코드로 알림이 도착했다(1번은 애초에 임계치를 안 넘어서 알림이 없는 게 맞는 동작이다). 2번이 이 실험 전체에서 가장 중요한 결과다 - **정상 상태 가설을 지킨다고 믿었던 알림 규칙이, 실제로는 그 장애 유형(재시작 없이 즉사하는 OOMKill)을 애초에 탐지할 수 없는 조건식이었다는 게 실험으로 드러났다.** "장애를 일으켜봤다"가 아니라 "탐지 공백을 찾아 메꿨다"가 카오스 엔지니어링의 진짜 산출물이라는 걸 보여주는 사례다 - 만약 이 실험을 하지 않았다면, 실제 운영 중 조용히 재시작 없이 죽는 파드가 생겨도 알림 없이 방치됐을 것이다.

## 포스트모템 문서 템플릿

실험마다 아래 형식으로 기록한다. 항목을 미리 정해두는 이유는, 장애가 실제로 터졌을 때(연습이 아니라 진짜 사고일 때) 같은 틀로 돌아볼 수 있게 훈련하는 것도 이 실험의 목적이기 때문이다.

```markdown
# 포스트모템: <실험명> (YYYY-MM-DD)

## 타임라인
- 00:00 장애 주입 (구체적 명령/조작)
- 00:XX 첫 이상 신호 감지 (메트릭/로그상 변화)
- 00:XX 알림 도착 (Discord 등)
- 00:XX 자동/수동 복구 완료

## 원인
(장애가 실제로 무엇 때문에 발생했는지)

## 탐지 공백
(장애 발생부터 알림 도착까지 얼마나 걸렸는지, 왜 그만큼 걸렸는지)

## 재발 방지
(알림 규칙 조정, 임계치 변경, 자동 복구 추가 등 - 실행한 조치)
```

## 검증 방법

각 실험에서 반드시 남겨야 하는 숫자 3가지: **장애 발생 시각**, **첫 메트릭/로그 이상 시각**, **알림 도착 시각**. 이 세 시각의 차이가 곧 "탐지 공백(detection gap)"이고, 이 값을 계속 줄여나가는 게 알림 규칙 튜닝의 목표다. 나중에 [SLO/에러 버짓](/blog/devops-roadmap-07-sli-slo-error-budget)을 잡을 때도 이 탐지 공백이 "장애가 나서 실제로 사용자 영향이 시작되는 시점"과 "우리가 그걸 알게 되는 시점" 사이의 간극으로 그대로 이어진다.
