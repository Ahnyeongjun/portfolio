## AWS 기본 개념

**Region**: 물리적으로 분리된 데이터센터 집합. `ap-northeast-2` (서울), `us-east-1` (버지니아).

**AZ (Availability Zone)**: 한 Region 내의 독립 데이터센터. 서울 Region에 4개. 한 AZ가 장애나도 다른 AZ는 정상.

**VPC (Virtual Private Cloud)**: AWS 내 격리된 가상 네트워크. 서브넷으로 나눈다.

```
VPC (10.0.0.0/16)
├── Public Subnet (10.0.1.0/24) - 인터넷 접근 가능 (ALB, NAT)
├── Private Subnet (10.0.2.0/24) - 내부만 (ECS, EC2)
└── DB Subnet (10.0.3.0/24) - DB만 (RDS)
```

## 컴퓨팅

### EC2

가상 서버. 직접 OS 수준 접근 필요할 때.

**인스턴스 타입**:
- `t3.medium` - 범용, 버스터블 CPU
- `m5.large` - 균형 잡힌 메모리/CPU
- `c5.large` - CPU 집약
- `r5.large` - 메모리 집약 (DB, Redis)

**비용 최적화**:
- On-Demand: 기본. 시간당 요금.
- Reserved: 1~3년 약정. 최대 72% 할인.
- Spot: 여유 용량 경매. 최대 90% 할인. 언제든 회수됨 → 무상태 작업에 적합.

### ECS Fargate

컨테이너 관리형 서비스. EC2 인스턴스를 직접 관리하지 않아도 된다.

```
ECS Cluster
└── Service (원하는 Task 수 유지)
    └── Task (컨테이너 실행 단위)
        └── Container
```

```json
// Task Definition
{
  "family": "app",
  "cpu": "512",
  "memory": "1024",
  "containerDefinitions": [{
    "name": "app",
    "image": "123456789.dkr.ecr.ap-northeast-2.amazonaws.com/app:latest",
    "portMappings": [{"containerPort": 8080}],
    "environment": [
      {"name": "SPRING_PROFILES_ACTIVE", "value": "prod"}
    ],
    "secrets": [
      {"name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:..."}
    ]
  }]
}
```

### ALB (Application Load Balancer)

HTTP/HTTPS 트래픽을 여러 대상으로 분산.

```
인터넷 → ALB
         ├── /api/* → ECS Service A (API 서버)
         └── /admin/* → ECS Service B (어드민)
```

**Target Group**: 트래픽을 받는 대상 그룹. Health Check로 비정상 대상은 제외.

## 비용 최적화 실전

### NAT Gateway 비용 문제

Private Subnet의 인스턴스가 인터넷(외부 API, 패키지 저장소)에 나가려면 NAT Gateway를 거친다. 문제는 **시간당 요금 + 처리한 데이터 GB당 요금**이 이중으로 부과된다는 점이다. AZ마다 하나씩 두면(고가용성 목적) 트래픽이 많은 서비스에서는 월 수십~수백만 원 단위로 청구서에 잡힌다.

```
EC2/ECS (Private Subnet) → NAT Gateway → Internet Gateway → S3 (인터넷 경유, 과금 발생)
```

**VPC Endpoint로 우회**:

```
Gateway 타입 (S3, DynamoDB만 지원, 무료):
EC2 → VPC Endpoint(Gateway) → S3     # NAT Gateway/인터넷 안 거침, 라우팅 테이블에 항목 추가만

Interface 타입 (나머지 대부분 AWS 서비스, ENI 기반, 시간당 요금 있음):
EC2 → VPC Endpoint(Interface, ENI) → Secrets Manager / ECR / CloudWatch Logs
```

S3/DynamoDB를 많이 호출하는 워크로드라면 Gateway Endpoint 하나 추가하는 것만으로 NAT Gateway 데이터 처리 비용이 크게 줄어든다. ECR에서 이미지를 자주 pull하는 ECS/EKS 클러스터도 Interface Endpoint(`com.amazonaws.<region>.ecr.dkr`, `ecr.api`, `s3`)를 붙이면 NAT 비용과 이미지 pull 지연을 동시에 줄일 수 있다.

### Savings Plans vs Reserved Instance

| 항목 | Savings Plans | Reserved Instance |
|------|---------------|-------------------|
| 적용 범위 | EC2/Fargate/Lambda 등 컴퓨팅 전체 | 특정 인스턴스 패밀리/리전에 고정 |
| 유연성 | 인스턴스 타입 변경해도 할인 유지 | 타입 변경 시 할인 깨지거나 교환 필요 |
| 할인율 | 최대 ~66% (1년/3년, 선불 정도에 따라) | 최대 ~72% |
| 적합한 상황 | 워크로드가 계속 변하는 조직(마이크로서비스 확장/축소 잦음) | 인스턴스 구성이 오래 고정되는 레거시/DB 서버 |

실무에서는 **베이스라인 트래픽(항상 켜져 있는 최소 용량)만 Savings Plans/RI로 커버하고, 피크 트래픽은 On-Demand나 Spot(무상태 배치 작업)으로 흡수**하는 조합을 쓴다. 기준선을 잘못 잡아 RI를 과다 구매하면 트래픽이 줄어도 환불이 안 되는 매몰비용이 된다.

### S3 스토리지 클래스 라이프사이클

```json
// S3 Lifecycle Rule
{
  "Rules": [{
    "Status": "Enabled",
    "Transitions": [
      {"Days": 30,  "StorageClass": "STANDARD_IA"},
      {"Days": 90,  "StorageClass": "GLACIER_IR"},
      {"Days": 365, "StorageClass": "DEEP_ARCHIVE"}
    ],
    "Expiration": {"Days": 1825}
  }]
}
```

접근 빈도가 예측 가능한 데이터(로그, 백업)는 생성 후 30일이 지나면 조회가 급격히 줄어드는 패턴이 흔하다. Standard에 방치하면 GB당 요금이 가장 비싼 구간에 계속 머문다. `S3 Intelligent-Tiering`을 쓰면 접근 패턴을 자동 분석해 클래스를 옮겨주므로, 접근 패턴이 불규칙한 데이터에는 수동 라이프사이클보다 이게 낫다.

## 데이터베이스

### RDS

관리형 RDB. MySQL, PostgreSQL, Aurora 지원.

```
Multi-AZ 배포:
                Primary (ap-northeast-2a)
                    ↕ 동기 복제
                Standby (ap-northeast-2c)  ← 자동 장애조치 (Failover)
```

**Read Replica**: 읽기 전용 복제본. 읽기 부하 분산.

```
애플리케이션
├── 쓰기 → Primary RDS
└── 읽기 → Read Replica (최대 5개)
```

**주요 설정**:
```
Multi-AZ: 고가용성 (약 2배 비용)
자동 백업: 1~35일 보관
Parameter Group: DB 설정값 (max_connections, shared_buffers 등)
```

### Aurora

AWS 전용 클라우드 최적화 RDB. MySQL/PostgreSQL 호환.

- 자동 스토리지 증가 (10GB~128TB)
- 6개 AZ에 6개 복사본 자동 유지
- Read Replica를 15개까지 지원
- RDS MySQL 대비 5배, PostgreSQL 대비 3배 성능

## 스토리지

### S3

객체 스토리지. 파일, 이미지, 백업, 정적 자산.

```java
// Spring Boot S3 업로드
@Service
public class S3Service {
    private final S3Client s3Client;
    private final String bucketName;

    public String upload(MultipartFile file, String key) {
        PutObjectRequest request = PutObjectRequest.builder()
            .bucket(bucketName)
            .key(key)
            .contentType(file.getContentType())
            .build();

        s3Client.putObject(request,
            RequestBody.fromInputStream(file.getInputStream(), file.getSize()));

        return "https://%s.s3.amazonaws.com/%s".formatted(bucketName, key);
    }
}
```

**Presigned URL**: 임시 업로드/다운로드 URL. 클라이언트가 S3에 직접 업로드할 때.

```java
// Presigned URL 생성 (15분 유효)
PresignedPutObjectRequest presigned = presigner.presignPutObject(req ->
    req.signatureDuration(Duration.ofMinutes(15))
       .putObjectRequest(r -> r.bucket(bucketName).key(key)));

return presigned.url().toString();
```

**S3 버킷 정책**:
- Public: 정적 웹사이트 호스팅
- Private + Presigned URL: 임시 접근
- Private + CloudFront: CDN을 통한 배포

## 메시지 큐

### SQS (Simple Queue Service)

```
Producer → SQS Queue → Consumer (Poll 방식)
```

**Standard Queue**: 최소 1회 배달, 순서 미보장, 높은 처리량.

**FIFO Queue**: 정확히 1회 배달, 순서 보장, 처리량 제한 (초당 300~3000).

```java
// Spring Cloud AWS SQS
@SqsListener("order-queue")
public void handleOrder(OrderMessage message) {
    orderService.process(message);
}
```

**DLQ (Dead Letter Queue)**: 처리 실패한 메시지를 별도 큐로. 재시도 횟수 초과 시.

## IAM (Identity and Access Management)

AWS 리소스 접근 제어.

**IAM Role**: EC2, ECS Task에 권한 부여. Access Key 없이 안전하게.

```json
// ECS Task Role: S3와 Secrets Manager 접근 허용
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::my-bucket/*"
    },
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:ap-northeast-2:*:secret:prod/*"
    }
  ]
}
```

**최소 권한 원칙**: 필요한 최소한의 권한만 부여. `*` 권한은 절대 사용 금지.

### IRSA (IAM Roles for Service Accounts)

EKS에서 파드가 AWS 자원에 접근해야 할 때, EC2 Instance Profile을 쓰면 **같은 노드에서 도는 모든 파드가 그 노드의 권한을 전부 공유**한다. 파드 A가 S3만 필요해도, 노드에 실려있으면 파드 B(다른 팀 워크로드)도 같은 권한으로 노드의 자격증명을 훔쳐 쓸 수 있다.

IRSA는 **OIDC(OpenID Connect) 페더레이션**으로 이 문제를 없앤다. EKS 클러스터가 OIDC Provider로 등록되고, Kubernetes ServiceAccount와 IAM Role을 1:1로 매핑해 파드 단위로 권한을 준다.

```yaml
# ServiceAccount에 IAM Role ARN을 annotation으로 연결
apiVersion: v1
kind: ServiceAccount
metadata:
  name: order-service-sa
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/order-service-role
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      serviceAccountName: order-service-sa  # 이 파드만 해당 Role의 권한을 가짐
```

```json
// IAM Role의 Trust Policy - 이 ServiceAccount에서 온 토큰만 AssumeRole 허용
{
  "Effect": "Allow",
  "Principal": {"Federated": "arn:aws:iam::123456789:oidc-provider/oidc.eks.ap-northeast-2.amazonaws.com/id/XXXX"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "oidc.eks...:sub": "system:serviceaccount:default:order-service-sa"
    }
  }
}
```

핵심은 **파드가 노드의 자격증명이 아니라, 자기 ServiceAccount 토큰으로 STS에서 임시 자격증명을 직접 발급받는다**는 것이다. 노드가 탈취돼도 그 노드의 다른 파드 권한으로는 이 파드의 리소스에 접근할 수 없다.

### AssumeRole과 크로스 계정 접근

멀티 계정 구조(운영/스테이징/개발 계정 분리)에서 한 계정의 사용자가 다른 계정의 리소스에 접근해야 할 때 Access Key를 공유하지 않고 Role을 임시로 위임받는다.

```bash
aws sts assume-role \
  --role-arn arn:aws:iam::999999999:role/cross-account-readonly \
  --role-session-name my-session
# 반환된 임시 자격증명(AccessKeyId, SecretAccessKey, SessionToken, 기본 1시간 만료)으로 API 호출
```

CI/CD 파이프라인이 배포 계정에서 운영 계정으로 배포할 때도 이 방식을 쓴다. 장기 Access Key를 파이프라인에 심어두지 않아도 되고, Trust Policy로 "어떤 계정/역할만 AssumeRole 가능한지"를 명시적으로 제한할 수 있다.

### 최소 권한을 실제로 검증하기: IAM Access Analyzer

정책을 "최소 권한으로 짰다"는 주장은 실제로 그 Role이 어떤 API를 호출하는지 관찰하기 전까진 추정일 뿐이다. **IAM Access Analyzer**는 CloudTrail 로그 기반으로 실제 사용된 액션만 모아 정책 초안을 생성해준다.

```
IAM Access Analyzer → Policy Generation
  1. 관찰 기간(예: 90일) 지정
  2. 해당 Role/User가 실제로 호출한 API 액션을 CloudTrail에서 수집
  3. "실제로 쓴 액션만" 포함된 최소 권한 정책 초안 생성
  4. 검토 후 기존 광범위한 정책을 이 초안으로 교체
```

외부 계정/퍼블릭 접근을 허용하는 리소스(S3 버킷 정책, KMS 키 정책 등)도 Access Analyzer가 자동으로 탐지해 알려준다. "의도한 공유"와 "실수로 열린 접근"을 구분하는 게 핵심 용도다.

## 재해 복구 (DR)

### RTO / RPO

**RTO (Recovery Time Objective)**: 장애 발생 후 서비스가 다시 정상화되기까지 허용 가능한 시간.

**RPO (Recovery Point Objective)**: 장애 시점에 잃어도 되는 데이터의 최대 시간 범위. "RPO 5분"이면 백업 주기가 5분보다 길면 안 된다.

이 두 숫자가 DR 전략을 결정한다. RTO/RPO가 짧을수록(0에 가까울수록) 비용이 기하급수적으로 올라간다.

### 전략별 비교

| 전략 | 구성 | RTO | RPO | 상시 비용 |
|------|------|-----|-----|-----------|
| Backup & Restore | 백업만 다른 리전에 보관, 장애 시 처음부터 인프라 구축 | 시간~일 단위 | 백업 주기(수 시간) | 최소 (스토리지 비용만) |
| Pilot Light | DR 리전에 최소 구성(DB만 복제 유지)만 켜두고, 나머지는 장애 시 기동 | 수십 분~시간 | 수 분 (DB 복제 지연) | 낮음 |
| Warm Standby | DR 리전에 축소된 버전(적은 용량)을 상시 가동, 장애 시 스케일업 | 수 분 | 수 분 이하 | 중간 (DR 리전도 계속 과금) |
| Multi-Site Active-Active | 두 리전 모두 풀 트래픽 처리, 장애 시 라우팅만 전환 | 초 단위 | ~0 | 높음 (2배 인프라 상시 운영) |

**실무에서 어떻게 고르는가**: 결제·인증처럼 장애가 매출/신뢰에 직결되는 서비스는 Warm Standby 이상, 배치/집계처럼 몇 시간 늦어도 되는 워크로드는 Backup & Restore로 충분하다. RTO/RPO를 서비스 등급별로 나눠 정하지 않고 전체 시스템에 동일한 기준을 적용하면 불필요한 비용이 발생한다.

### Aurora Global Database

Aurora는 리전 간 복제를 위한 전용 기능을 제공한다.

```
Primary Region (쓰기)
    ↓ 스토리지 레벨 복제 (평균 1초 이내, 비동기)
Secondary Region (읽기 전용, 장애 시 수동/자동 승격 가능)
```

일반 Cross-Region Read Replica(MySQL/PostgreSQL 표준 복제)는 **트랜잭션 로그 기반 논리 복제**라서 리전 간 지연이 초 단위 이상으로 커질 수 있고, 승격(promotion) 과정에서 몇 분이 걸린다. Aurora Global Database는 **스토리지 계층에서 직접 복제**하기 때문에 지연이 훨씬 짧고(<1초), `managed planned failover`로 승격도 수십 초 내에 끝난다. RPO를 초 단위로 맞춰야 하는 글로벌 서비스가 아니면 비용 대비 일반 Read Replica로도 충분한 경우가 많다.

## 암호화

### KMS와 Envelope Encryption

AWS 서비스 대부분(S3, RDS, EBS)의 "저장 시 암호화(Encryption at Rest)"는 데이터를 KMS 키로 직접 암호화하지 않는다. **Envelope Encryption** 구조를 쓴다.

```
1. KMS의 CMK(Customer Master Key)는 리전 밖으로 절대 나가지 않는다
2. 데이터를 암호화할 때마다 CMK로 "데이터 키(Data Key)"를 새로 생성
3. 실제 데이터는 이 데이터 키로 암호화 (빠름, 로컬에서 처리)
4. 데이터 키 자체는 CMK로 암호화해서 데이터와 함께 저장
5. 복호화 시: 암호화된 데이터 키를 KMS에 보내 복호화 → 그 데이터 키로 데이터 복호화
```

이렇게 하면 대용량 데이터를 KMS API로 매번 왕복시키지 않고도(느리고 API 호출 제한 있음), CMK는 안전하게 보관하면서 실제 암복호화는 로컬에서 빠르게 처리할 수 있다.

**서비스별 암호화 계층**:

| 서비스 | 암호화 위치 | 특징 |
|--------|------------|------|
| EBS | 볼륨 블록 단위 | 스냅샷도 자동으로 암호화 상태 유지 |
| S3 (SSE-KMS) | 객체 단위 | 객체별로 다른 데이터 키 사용 가능 |
| RDS | 스토리지 + 자동 백업 + 스냅샷 + Read Replica | 암호화 안 된 인스턴스 → 암호화 인스턴스로 전환은 스냅샷 재생성 필요 (즉시 전환 불가) |

**키 로테이션**: CMK 자동 로테이션(연 1회)을 켜면 백엔드 키 자재만 바뀌고 기존에 암호화된 데이터 키의 참조는 유지된다 - 재암호화가 필요 없다. 다만 규정상 특정 주기로 "완전히 새 키로 재암호화"를 요구하면(ISMS-P 등 일부 컴플라이언스) 별도 마이그레이션 절차가 필요하다.

## 네트워크 연결: VPC Peering vs Transit Gateway

### VPC Peering의 한계

```
VPC A ↔ VPC B   (Peering 1개)
VPC A ↔ VPC C   (Peering 2개)
VPC B ↔ VPC C   (Peering 3개)
```

VPC가 N개면 전체를 서로 연결(Full Mesh)하려면 Peering이 `N(N-1)/2`개 필요하다. VPC가 10개면 45개. 라우팅 테이블도 VPC마다 각 Peering 대상에 대한 항목을 일일이 추가해야 하고, **Peering은 전이성(Transitive)이 없어서** A-B, B-C가 연결돼도 A가 C와 통신하려면 반드시 별도로 A-C를 맺어야 한다.

### Transit Gateway

```
VPC A ─┐
VPC B ─┼─ Transit Gateway (중앙 허브) ─┬─ On-premise (VPN/Direct Connect)
VPC C ─┘                              └─ 다른 계정의 VPC
```

허브-스포크 구조로 바꿔서 VPC마다 Transit Gateway 하나에만 연결하면 된다. VPC가 늘어나도 연결 개수는 선형(N개)으로만 증가하고, 라우팅도 Transit Gateway 라우팅 테이블 하나에서 중앙 관리한다. 온프레미스 VPN/Direct Connect까지 한 허브에 붙일 수 있어 하이브리드 구성에도 유리하다.

**언제 Peering으로 충분한가**: VPC 2~3개 규모로 고정되어 있고 늘어날 계획이 없으면 Peering이 더 단순하고 비용도 낮다(Transit Gateway는 attachment당 + 처리 데이터당 과금). 계정/VPC 수가 늘어날 예정이거나 온프레미스 연결이 섞이면 처음부터 Transit Gateway로 설계하는 게 나중에 마이그레이션하는 것보다 싸다.

## EKS 운영: Managed Node Group vs Fargate Profile

| 항목 | Managed Node Group | Fargate Profile |
|------|--------------------|------------------|
| 인프라 관리 | EC2 인스턴스는 여전히 직접 관리(패치는 관리형이 지원) | 서버리스, 노드 개념 없음 |
| DaemonSet | 정상 동작 (노드가 실재하므로) | 지원 안 됨 (노드가 없어서 - 로깅/모니터링 에이전트를 DaemonSet으로 깔던 방식이 안 통함) |
| 특수 워크로드 | GPU, 특정 인스턴스 타입, 노드 로컬 캐시 활용 가능 | 파드당 격리된 마이크로 VM, 노이지 네이버 문제 없음 |
| 스케일링 속도 | Cluster Autoscaler/Karpenter로 노드 증설, 분 단위 | 파드 단위로 즉시 프로비저닝, 노드 대기 없음 |
| 비용 | 노드 단위 과금(빈 자리 낭비 가능) | 파드가 실제 쓴 vCPU/메모리만큼 정확히 과금 |

DaemonSet으로 로그/메트릭 에이전트를 깔아야 하는 클러스터, GPU 워크로드, 인스턴스 타입을 세밀하게 고르고 싶은 경우는 Managed Node Group. 트래픽이 튀는 배치성 워크로드나 팀별로 완전히 격리된 실행 환경이 필요하면 Fargate Profile. 실무에서는 **상시 서비스는 Managed Node Group + Karpenter로 노드 최적화, 예측 어려운 배치 작업은 별도 Fargate Profile**로 섞어 쓰는 구성이 흔하다.

### 관찰성

```yaml
# CloudWatch Container Insights - 클러스터/노드/파드 단위 CPU·메모리·네트워크 자동 수집
# EKS 애드온으로 설치
aws eks create-addon --cluster-name my-cluster --addon-name amazon-cloudwatch-observability
```

분산 추적은 **AWS X-Ray**를 붙이면 ALB → EKS 파드 → RDS/외부 API까지 요청 흐름의 각 구간 지연을 시각화할 수 있다. 자체 구축한 Prometheus/Grafana/Jaeger 스택 대신 관리형으로 빠르게 시작할 때 선택하지만, PromQL 기반 커스텀 알람이나 온프레미스와 통일된 관찰성 스택이 필요하면 오픈소스 조합이 여전히 더 유연하다.

## 면접에서 자주 나오는 질문

**Q. EC2와 ECS Fargate의 차이는?**

EC2는 가상 서버를 직접 관리한다. OS 패치, 스케일링, 인스턴스 관리를 직접 해야 한다. ECS Fargate는 서버리스 컨테이너 서비스다. EC2를 직접 관리하지 않고 컨테이너 단위로 CPU/메모리를 지정하면 AWS가 인프라를 관리한다.

**Q. S3에 직접 업로드하는 방법은?**

Presigned URL을 사용한다. 서버가 Presigned URL을 생성해 클라이언트에 전달하면, 클라이언트가 서버를 거치지 않고 S3에 직접 업로드한다. 서버 대역폭을 절약하고 업로드 속도가 빠르다.

**Q. RDS Multi-AZ와 Read Replica의 차이는?**

Multi-AZ는 고가용성을 위한 것이다. 동기 복제로 Primary 장애 시 Standby가 자동으로 Primary가 된다. Read Replica는 성능을 위한 것이다. 비동기 복제로 읽기 부하를 분산한다. Multi-AZ Standby는 읽기에 사용할 수 없다.

**Q. IAM Role과 IAM User의 차이는?**

IAM User는 사람 또는 애플리케이션을 위한 영구적인 자격증명(Access Key). IAM Role은 AWS 서비스(EC2, Lambda, ECS)에 임시로 부여하는 권한이다. EC2나 ECS에서 AWS SDK를 쓸 때 Role을 사용하면 Access Key를 코드에 넣지 않아도 된다.

**Q. NAT Gateway 비용을 줄이는 구체적인 방법은?**

가장 큰 비용 요인은 처리 데이터량(GB당 요금)이다. S3/DynamoDB로 나가는 트래픽은 Gateway 타입 VPC Endpoint를 붙이면 NAT Gateway를 전혀 거치지 않고 무료로 라우팅된다. ECR, Secrets Manager, CloudWatch Logs처럼 자주 호출하는 서비스는 Interface 타입 Endpoint(ENI 기반, 시간당 요금은 있지만 데이터 처리 요금이 NAT보다 저렴한 경우가 많음)를 붙인다. AZ마다 하나씩 두던 NAT Gateway를 트래픽이 크지 않은 환경이라면 1개로 통합하고 대신 가용성 리스크를 감수하는 선택도 비용 민감도에 따라 가능하다.

**Q. IRSA가 EC2 Instance Profile보다 안전한 이유는?**

Instance Profile은 노드 단위로 권한이 부여돼서, 같은 노드에 뜬 모든 파드가 그 권한을 공유한다. 파드 하나가 침해당하면 노드의 전체 권한이 노출된다. IRSA는 OIDC 페더레이션으로 Kubernetes ServiceAccount와 IAM Role을 1:1 매핑해서, 파드가 노드가 아니라 자기 자신의 자격증명으로 STS에서 임시 크리덴셜을 발급받는다. 권한의 경계가 노드에서 파드 단위로 좁아진다.

**Q. RTO/RPO 기준으로 재해복구 전략을 어떻게 고르는가?**

먼저 서비스별로 "장애 시 몇 분/시간 안에 복구해야 하는가(RTO)"와 "몇 분치 데이터까지는 잃어도 되는가(RPO)"를 정한다. 결제·인증처럼 직접 매출과 신뢰에 영향을 주는 서비스는 RTO/RPO를 짧게 잡고 Warm Standby 이상(상시 축소 인프라 가동)을 쓴다. 배치·집계처럼 지연이 용인되는 워크로드는 Backup & Restore로 비용을 아낀다. 모든 서비스에 동일한 DR 등급을 적용하면 불필요한 상시 비용이 발생하므로, 서비스 중요도별로 등급을 나누는 게 핵심이다.

**Q. VPC Peering이 커지면 왜 문제가 되고 Transit Gateway로 어떻게 해결하는가?**

Peering은 전이성이 없어서 A-B, B-C를 맺어도 A-C는 별도로 맺어야 하고, VPC가 N개면 최대 N(N-1)/2개의 연결과 각각의 라우팅 테이블 항목이 필요해 관리가 기하급수적으로 복잡해진다. Transit Gateway는 허브-스포크 구조로 VPC마다 허브 하나에만 연결하면 되므로 연결 개수가 VPC 수에 선형으로만 증가하고, 라우팅도 중앙에서 한 번에 관리한다.

**Q. Aurora Global Database와 일반 Cross-Region Read Replica의 차이는?**

일반 Read Replica는 트랜잭션 로그 기반 논리 복제라서 리전 간 지연이 초 단위 이상으로 벌어질 수 있고 승격에도 몇 분이 걸린다. Aurora Global Database는 스토리지 계층에서 직접 복제하기 때문에 지연이 1초 이내로 훨씬 짧고, managed planned failover로 승격도 수십 초 내에 끝난다. RPO를 초 단위로 맞춰야 하는 글로벌 서비스가 아니라면 비용 대비 일반 Read Replica로 충분한 경우가 많다.
