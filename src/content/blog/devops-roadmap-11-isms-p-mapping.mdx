## 목표

이 시리즈에서 "인증"은 로그인(authentication)이 아니라 **심사(certification) 대응**이다. 지금까지 만든 인프라(NetworkPolicy, TLS, SealedSecret, Loki)를 심사원이 물었을 때 무엇을 열어 보여줄지 - 증적(evidence) 관점으로 다시 정리하는 게 목표다.

## 개념: ISMS-P란 무엇인가, 그리고 "증적"이란

**ISMS-P(정보보호 및 개인정보보호 관리체계 인증)**는 조직이 정보보호·개인정보보호를 위한 관리 체계를 제대로 갖추고 운영하는지 국가 기관(KISA)이 심사해서 인증해주는 제도다. 여기서 "인증"은 로그인 인증이 아니라 **자격을 공식적으로 확인해주는 절차(certification)**를 뜻한다 - 회사가 "우리는 이런 기준들을 지키고 있다"를 스스로 주장하는 게 아니라, 외부 심사원이 실제로 확인하고 도장을 찍어주는 것이다.

심사는 "이런 정책이 있다"는 말로 끝나지 않는다. 심사원은 항상 **증적(evidence)** - 그 정책이 실제로 적용되고 있다는 걸 보여주는 구체적인 자료(설정 화면, 로그, 정책 파일, 테스트 결과) - 을 요구한다. 예를 들어 "서비스 간 통신을 제한하고 있다"는 주장은 `NetworkPolicy` YAML 파일 자체, 그리고 실제로 차단되는 걸 보여주는 테스트 로그가 있어야 증적으로 인정된다. **구현이 있다는 것과 증적이 준비돼 있다는 것은 다른 문제**라는 게 이 시리즈 전체를 관통하는 전제다.

**NetworkPolicy란**: Kubernetes 기본값은 "클러스터 안의 모든 파드가 서로 통신 가능"이다. NetworkPolicy는 특정 파드에 대해 "이 출발지에서 오는 트래픽만 허용한다"는 규칙을 선언하는 리소스다 - 방화벽 규칙을 파드 단위로 세밀하게 거는 것과 비슷하다. 아래 2번에서 이걸로 실제 통신 매트릭스를 강제한다.

## 실제 구축 절차

### 1. 매핑표 작성

KISA 「ISMS-P 인증기준 안내서」의 인프라 관련 항목을 확인하고(항목 번호·명칭은 원문 확인 후 정정), `security/isms-p/mapping.md`에 아래 형식으로 작성한다.

```markdown
| 인증기준 영역 | 이 프로젝트에서의 구현 | 증적(심사원에게 보여줄 것) | 상태 |
|---|---|---|---|
| 2.5 인증 및 권한관리 | Keycloak (정책·MFA·RBAC) | Realm 정책 화면, 클라이언트별 Role | 완료 |
| 2.6 접근통제 | Envoy SecurityPolicy, NetworkPolicy | HTTPRoute/Policy 정의, 통신 매트릭스 | 진행중 |
| 2.7 암호화 적용 | TLS, SealedSecret | 인증서 체계, 시크릿 관리 흐름 | 진행중 |
| 2.9 시스템·서비스 운영관리 | Loki 로그 보존, 백업 | 보존 정책 설정, 로그 접근 통제 | 진행중 |
| 2.10 시스템·서비스 보안관리 | Harbor+Trivy 이미지 스캔, 패치 이력 | CI 스캔 결과, 취약 이미지 배포 차단 정책, 업그레이드 기록 | 미착수 |
```

"구현"과 "증적"을 분리해서 적는 게 핵심이다 - NetworkPolicy를 적용했다는 사실 자체는 구현이고, 심사원에게 실제로 보여줄 것(정책 YAML, 실제 차단된 통신 로그, 통신 매트릭스 문서)은 증적이다. 구현은 있는데 증적이 정리 안 된 항목이 실제로 제일 많다.

### 2. 접근통제 - NetworkPolicy로 통신 매트릭스 만들기

먼저 서비스 간 통신 관계를 표로 정리한다.

```
게이트웨이 → api-server (허용)
api-server → RabbitMQ (허용)
api-server → PostgreSQL (허용)
inference-worker → RabbitMQ (허용)
inference-worker → PostgreSQL (허용)
그 외 모든 경로 (기본 차단)
```

이 표를 그대로 NetworkPolicy로 옮긴다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-server-ingress
  namespace: app
spec:
  podSelector:
    matchLabels: {app: api-server}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: gateway-system}
      ports:
        - port: 8000
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: app
spec:
  podSelector: {}
  policyTypes: [Ingress]
  # from을 지정하지 않음 - 명시적으로 허용되지 않은 모든 인그레스 차단
```

적용 후 반드시 **차단이 실제로 되는지** 검증한다.

```bash
# app 네임스페이스 밖에서 api-server에 직접 접근 시도 - 실패해야 정상
kubectl run test-pod --rm -it --image=busybox -n default -- \
  wget -qO- http://api-server.app.svc.cluster.local:8000/healthz
```

이 실패 로그(또는 허용된 통신의 성공 로그) 자체가 "통신 매트릭스가 실제로 강제되고 있다"는 증적이 된다.

### 3. 암호화 - TLS와 SealedSecret 증적 정리

TLS는 Envoy Gateway의 리스너 설정과 인증서 발급 이력(cert-manager 사용 시 `Certificate` 리소스 상태)을 캡처해둔다.

```bash
kubectl get certificate -A
kubectl describe certificate <name>   # 발급자, 만료일, 갱신 이력 확인
```

SealedSecret은 "평문이 Git에 올라간 적이 없다"는 걸 증명하는 게 핵심이다.

```bash
# Git 히스토리 전체에서 평문 시크릿이 커밋된 적이 없는지 확인
git log --all -p -- '*.yaml' | grep -i "password\|secret" | grep -v "SealedSecret\|sealedsecrets"
```

이 grep 결과가 비어있다는 것 자체를 증적 문서에 "검증 완료"로 남긴다.

### 4. 로그 - Loki 보존 정책 증적

시리즈 6에서 설정한 `retention_period`가 실제로 적용되고 있는지 확인한다.

```bash
# Loki 설정값 확인
kubectl get configmap loki -n monitoring -o yaml | grep retention_period

# 실제로 30일 이전 로그가 조회되지 않는지 확인
logcli query '{namespace="app"}' --from="$(date -d '31 days ago' --iso-8601=seconds)" --limit=10
```

로그 접근 통제(누가 Grafana/Loki에 접근할 수 있는지)도 RBAC 설정을 캡처해둔다.

### 5. 모의 심사 - 항목별 문답 준비

각 항목마다 "심사원이 이렇게 물으면, 나는 이 화면/파일을 연다"는 형식으로 정리한다.

```markdown
Q. 서비스 간 통신이 필요한 경로로만 제한되어 있다는 걸 어떻게 증명합니까?
A. security/isms-p/network-matrix.md의 통신 매트릭스 표 +
   kubectl get networkpolicy -A 출력 +
   default-deny 정책이 있다는 것 + 차단 테스트 로그

Q. 시크릿이 평문으로 저장소에 노출된 적이 없다는 걸 어떻게 압니까?
A. 전체 Git 히스토리에 대한 grep 검증 결과 (위 3번 절차) +
   SealedSecret 컨트롤러가 클러스터 안에서만 복호화 가능하다는 아키텍처 설명
```

### 6. 실제 심사에서 자주 걸리는 항목 - 정책과 구현의 격차

실무에서 심사원이 지적하는 패턴은 대체로 세 가지로 수렴한다.

**정책-구현 불일치.** mapping.md에는 "NetworkPolicy로 default-deny 적용"이라고 적혀 있는데, 실제 클러스터에서 `kubectl get networkpolicy -A`를 돌려보면 그 정책이 없거나 다른 네임스페이스에만 적용돼 있는 경우다. GitOps(Argo CD 등)로 배포하지 않고 `kubectl apply`로 급하게 패치하고 넘어간 이력이 있으면 Git의 YAML과 클러스터의 실제 상태가 갈라진다. 심사원은 문서가 아니라 클러스터를 보므로, 이 순간 격차가 그대로 드러난다. 이 시리즈에서 GitOps를 다룬 이유 중 하나가 여기 있다 - Git이 곧 "선언된 상태"이고 클러스터가 그와 다르면 그 자체가 이상 신호다.

**접근권한 검토 주기 미준수.** 정책서에 "RBAC 권한을 분기별로 검토한다"라고 써놓고 실제로는 한 번도 검토하지 않은 경우가 흔하다. 퇴사자나 역할이 바뀐 사람의 `ClusterRoleBinding`이 몇 달째 남아있는 걸 심사원이 `kubectl get clusterrolebinding -o wide`로 확인하면서 발견한다. 이건 기술 문제가 아니다 - RBAC YAML을 정확히 짜는 것과, "이 사람이 아직 이 권한이 필요한가"를 주기적으로 확인하는 것은 완전히 다른 작업이다. 후자는 캘린더에 반복 일정을 걸어두는 수준의 운영 프로세스이지만, 실제로 지켜지는 조직은 드물다.

**로그 보존기간 실제 미달.** `retention_period: 720h`(30일)로 설정해뒀다고 mapping.md에 "완료"로 적어놓고, 실제로 `logcli query`로 25일 전 로그를 조회하면 이미 없는 경우가 있다. 원인은 대개 스토리지 용량이다 - Loki의 컴팩터가 보존기간과 별개로 디스크 압박을 받으면 오래된 청크를 더 일찍 지운다. 설정값과 실제 동작이 다를 수 있다는 뜻이고, 이건 "설정했다"는 것과 "그 설정대로 동작하고 있다"는 것을 구분해야 하는 이유이기도 하다 - 증적은 설정 파일이 아니라 실제 조회 결과여야 한다.

이 세 케이스의 공통점은, 문서와 설정 파일만 보고 "구현됐다"고 판단했을 때 생기는 격차라는 것이다. 실제 상태를 주기적으로 재확인하지 않으면 이 격차는 심사 당일까지 아무도 모른다.

### 7. 증적의 지속성 - 스냅샷 한 장의 한계와 자동화

지금까지 정리한 절차 - `kubectl get networkpolicy`, `kubectl describe certificate`, Git 히스토리 grep - 를 심사 하루 전에 한 번 실행해서 캡처해두면 그 순간의 상태는 증명되지만, **그 이후에 누가 정책을 수정하거나 삭제해도 아무도 모른다.** 심사는 1년에 한 번이지만 클러스터는 매일 바뀐다. 스크린샷 한 장은 "그때는 맞았다"는 증거일 뿐, "지금도 맞다"는 증거가 아니다.

이 갭을 메우는 방법은 결국 자동화다 - 심사 시점에만 수동으로 캡처하는 게 아니라, 같은 검증을 주기적으로 실행해서 그 결과를 계속 쌓아두는 것.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: isms-p-evidence-scan
  namespace: security
spec:
  schedule: "0 3 * * *"  # 매일 새벽 3시
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: evidence-scanner  # 조회 전용 RBAC
          containers:
            - name: scan
              image: bitnami/kubectl:latest
              command:
                - /bin/sh
                - -c
                - |
                  kubectl get networkpolicy -A -o yaml > /report/networkpolicy-$(date +%F).yaml
                  kubectl get certificate -A -o json > /report/certificate-$(date +%F).json
                  kubectl get clusterrolebinding -o wide > /report/rbac-$(date +%F).txt
                  # 결과를 S3나 별도 Git 리포지토리에 업로드
              volumeMounts:
                - {name: report, mountPath: /report}
          restartPolicy: OnFailure
          volumes:
            - {name: report, emptyDir: {}}
```

이렇게 매일 쌓인 리포트는 두 가지 역할을 한다. 첫째, 심사 당일 "최근 90일간 이 정책이 계속 유지됐다"는 걸 날짜별 diff로 보여줄 수 있다 - 스냅샷 한 장보다 훨씬 강한 증적이다. 둘째, 리포트 생성 자체가 실패하거나 결과가 이전과 달라지면(예: default-deny 정책이 갑자기 사라짐) 알림을 걸 수 있어서, 심사 대비를 넘어 실제 드리프트 탐지 도구가 된다. mapping.md의 "증적" 컬럼도 이 관점에서 다시 써야 한다 - "정책 YAML"이 아니라 "정책 YAML + 최근 30일 스캔 리포트 링크"로.

### 8. 인프라 통제의 경계 - 인프라 엔지니어가 혼자 끝낼 수 없는 항목

매핑표를 채우다 보면 인프라만으로는 "완료"에 도달할 수 없는 항목들이 나온다. 정직하게 짚어두는 게 낫다.

- **2.5 인증 및 권한관리의 "권한 부여·회수 절차"** - Keycloak으로 RBAC 시스템 자체는 인프라가 구축할 수 있다. 하지만 "이 사람이 퇴사했으니 권한을 회수해야 한다"는 트리거는 인사 프로세스에서 나온다. 인프라 엔지니어가 인사 시스템과 연동을 만들어둘 수는 있어도, 그 연동이 실제로 매번 호출되는지는 조직의 퇴사 처리 프로세스가 지켜지느냐에 달려 있다.
- **2.6 접근통제의 "변경관리"** - 배포 전 승인 절차는 CI/CD 파이프라인에 "리뷰 승인 없이는 머지 불가", "프로덕션 배포는 별도 승인 필요" 같은 게이트를 걸어서 기술적으로 강제할 수 있다. 그런데 그 승인을 "누가, 무슨 기준으로 하는가"는 코드 리뷰 문화와 조직의 의사결정 구조에 달린 문제다. 인프라가 만들 수 있는 건 "승인 없이는 물리적으로 배포가 안 되는 파이프라인"까지고, "그 승인이 형식적인지 실질적인지"는 통제 밖이다.
- **2.10 시스템·서비스 보안관리의 "취약점 조치"** - Harbor+Trivy로 취약 이미지 배포를 자동으로 막는 것까지는 인프라 영역이다. 하지만 발견된 취약점을 실제로 패치하고 재배포하는 건 각 서비스를 담당하는 개발팀의 일이고, 그 조치가 SLA(예: Critical은 7일 이내) 안에 이뤄지는지는 인프라가 강제할 수 없다 - 배포를 막는 것과 고치는 것은 다른 사람의 책임이다.

이런 항목들에서 인프라 엔지니어의 역할은 "기술적으로 강제 가능한 지점까지 파이프라인에 게이트를 박아두고, 그 이후는 프로세스가 지켜지고 있다는 증거(승인 로그, SLA 준수율 등)를 개발팀·관리팀으로부터 받아서 매핑표에 채우는 것"으로 한정된다. 매핑표의 "상태"가 인프라 항목만 전부 "완료"여도 심사가 끝나지 않는 이유가 여기 있다 - 나머지는 인프라의 권한 밖에서 협조를 받아야 하는 항목들이다.

## 검증 방법

매핑표의 "상태" 컬럼이 전부 "완료"가 될 때까지 반복한다. 각 항목은 다음 세 가지가 모두 준비됐을 때만 "완료"로 표시한다 - **구현이 실제로 적용돼 있는가, 증적 자료가 실제로 존재하는가, 그 증적을 5분 안에 찾아서 보여줄 수 있는가.**

2.7 항목에 남은 숙제 하나 - SealedSecret은 "암호화된 값을 Git에 안전하게 커밋하는 것"에는 강하지만, **누가 언제 그 시크릿을 열람·변경했는지에 대한 감사 로그는 남기지 않는다.** "시크릿 접근 이력"까지 요구받으면 SealedSecret만으로는 답이 안 된다 - 이 갭을 어떻게 메울지(또는 메우지 않기로 할지)는 다음 편에서 다룬다.
