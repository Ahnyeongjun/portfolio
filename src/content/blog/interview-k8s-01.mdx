## K8s 핵심 오브젝트 복습

```
Cluster
└── Node (물리/가상 서버)
    └── Pod (컨테이너 실행 단위)
        └── Container

Deployment → ReplicaSet → Pod 관리
Service    → Pod 그룹에 안정적인 네트워크 엔드포인트
Ingress    → 외부 HTTP 트래픽 라우팅
ConfigMap  → 설정값 저장
Secret     → 민감 정보 저장
```

## Resource Request / Limit

```yaml
containers:
- name: app
  resources:
    requests:
      cpu: "250m"      # 0.25 코어 보장
      memory: "256Mi"  # 256MB 보장
    limits:
      cpu: "500m"      # 최대 0.5 코어
      memory: "512Mi"  # 최대 512MB
```

**Request**: 스케줄링 기준. 노드에 이 만큼의 여유가 있어야 Pod가 배치된다.

**Limit**: 초과 방지. CPU는 초과 시 스로틀링, 메모리는 초과 시 OOMKill.

**Request가 없으면**: 스케줄러가 자원 계획 없이 아무 노드에 배치 → 한 노드에 몰릴 수 있음.

**Limit이 없으면**: 하나의 Pod가 노드 자원을 전부 먹어 다른 Pod에 영향.

실무 권장: Request = Limit으로 설정 (Guaranteed QoS). 예측 가능한 성능.

## HPA (Horizontal Pod Autoscaler)

CPU/메모리 사용률에 따라 Pod 수를 자동으로 조절한다.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: app
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # CPU 70% 초과 시 스케일 아웃
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
```

**주의사항**:
- HPA가 동작하려면 `resources.requests`가 반드시 설정되어야 한다.
- 스케일 아웃은 빠르게, 스케일 인은 천천히 (기본 5분 안정화 기간).
- Spring Boot 같이 시작 시간이 긴 앱은 `startupProbe`를 추가해 준비 전에 트래픽이 안 들어오게.

## Cluster Autoscaler / Karpenter - 노드 단위 스케일링

HPA는 파드 수를 조절할 뿐, 노드 자체를 늘리거나 줄이지는 않는다. 노드에 여유가 없으면 HPA가 아무리 파드를 늘려도 `Pending` 상태로 쌓이기만 한다. 이 문제는 Cluster Autoscaler(또는 최신 대안인 Karpenter)가 해결한다.

```
HPA:                파드 수 조절 (CPU/메모리 사용률 기준, 초 단위 반응)
Cluster Autoscaler: 노드 수 조절 (Pending 파드 존재 여부 기준, 분 단위 반응)
```

**동시에 걸려있을 때 흐름**:

1. HPA가 CPU 사용률 초과 감지 → replica 증가 요청
2. 스케줄러가 새 파드를 배치할 노드를 탐색
3. 기존 노드에 자원이 부족 → 파드가 `Pending` 상태로 대기
4. Cluster Autoscaler가 Pending 파드를 감지 → 노드 그룹(ASG)에 노드 추가 요청
5. 새 노드가 Ready 상태가 되면(보통 1~3분) 스케줄러가 Pending 파드를 배치

```yaml
# Cluster Autoscaler 설정 예시 (AWS ASG 기반)
autoDiscovery:
  clusterName: my-cluster
extraArgs:
  scale-down-delay-after-add: 10m   # 노드 추가 후 10분간 스케일 다운 금지 (진동 방지)
  scale-down-unneeded-time: 10m     # 10분간 미사용 노드를 스케일 다운 후보로
```

**핵심은 지연 차이**다. 파드 스케일링은 초 단위, 노드 스케일링은 분 단위다. 그 사이 트래픽 급증에는 일부 요청이 지연되거나 실패할 수 있다. 급격한 스파이크가 예상되는 서비스는 `minReplicas`를 여유 있게 잡아 애초에 노드 추가가 필요 없는 여유분을 확보하거나, 예측 가능한 트래픽(세일, 배치 시간)에는 cron 기반으로 미리 스케일 업 해둔다. Karpenter는 노드 그룹이라는 중간 개념 없이 필요한 스펙의 노드를 즉시 프로비저닝해 이 지연을 줄인다.

## Taint/Toleration + Affinity + Topology Spread Constraints

**Taint/Toleration**: 노드에 "여기는 특별하다"는 표시(taint)를 하고, 그 표시를 견딜 수 있는(toleration) 파드만 배치되게 한다.

```bash
kubectl taint nodes gpu-node-1 workload=gpu:NoSchedule
```

```yaml
spec:
  tolerations:
  - key: "workload"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
  nodeSelector:
    workload: gpu
```

GPU 노드처럼 비용이 비싼 자원을 일반 워크로드가 우연히 차지하지 못하게 막는 용도로 흔히 쓴다.

**Node Anti-Affinity**: 같은 서비스의 파드가 같은 노드에 몰리지 않게 흩어놓는다.

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: my-service
      topologyKey: "kubernetes.io/hostname"
```

레플리카 3개가 전부 한 노드에 있으면, 그 노드가 죽는 순간 서비스가 통째로 죽는다. 표면적으로는 "고가용성 3 replica"인데 실제로는 단일 장애점(SPOF)인 경우가 실무에서 흔하다.

**Topology Spread Constraints**: Anti-affinity보다 세밀하게, AZ 단위로 균등 분산한다.

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: my-service
```

`maxSkew: 1`은 AZ 간 파드 수 차이를 최대 1개까지만 허용한다는 뜻이다. 3개 AZ에 레플리카 6개면 2/2/2로 분산되고, 한 AZ가 통째로 장애 나도 나머지 4개가 살아있다.

## 헬스체크 3종류

```yaml
containers:
- name: app
  # 시작 완료 여부 (시작 중에는 다른 프로브 비활성화)
  startupProbe:
    httpGet:
      path: /actuator/health
      port: 8080
    failureThreshold: 30    # 30번 실패하면 재시작 (30 * periodSeconds)
    periodSeconds: 10       # 최대 300초 대기

  # 트래픽 받을 준비가 됐는지
  readinessProbe:
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    initialDelaySeconds: 0
    periodSeconds: 5
    failureThreshold: 3     # 3번 실패하면 Service 엔드포인트에서 제외

  # 컨테이너가 살아있는지
  livenessProbe:
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    initialDelaySeconds: 30
    periodSeconds: 10
    failureThreshold: 3     # 3번 실패하면 컨테이너 재시작
```

**Spring Boot Actuator**:

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true  # /actuator/health/readiness, /actuator/health/liveness 활성화
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true
```

## PodDisruptionBudget (PDB)

노드 유지보수, kubectl drain 같은 **자발적 중단(Voluntary Disruption)** 시 최소 가용 Pod 수를 보장한다.

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
spec:
  minAvailable: 2       # 항상 최소 2개 유지
  # 또는
  maxUnavailable: 1     # 최대 1개까지 동시에 중단 허용
  selector:
    matchLabels:
      app: my-app
```

노드 업그레이드 시 PDB가 없으면 모든 Pod가 동시에 제거될 수 있다. PDB를 설정하면 순차적으로 제거되어 서비스가 유지된다.

## 배포 전략 상세

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 최대 1개 추가 생성 (기존 + 1)
      maxUnavailable: 0    # 항상 desired 수 유지 (무중단)
```

**무중단 배포 조건**:
1. `maxUnavailable: 0` 설정
2. `readinessProbe` 설정 (준비 완료 전 트래픽 차단)
3. 충분한 `terminationGracePeriodSeconds` (기본 30초)

```yaml
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60  # 60초 안에 정상 종료
      containers:
      - name: app
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 5"]
              # Service 엔드포인트에서 제거되기 전 5초 대기
              # 이 시간 동안 새 요청은 안 들어옴
```

```yaml
# ConfigMap: 일반 설정
apiVersion: v1
kind: ConfigMap

  name: app-config

  APP_ENV: "production"
  LOG_LEVEL: "INFO"

```

```yaml
# Secret: 민감 정보 (Base64 인코딩)
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
data:
  DB_PASSWORD: cGFzc3dvcmQxMjM=   # base64("password123")
  JWT_SECRET: c2VjcmV0a2V5MTIz
```

```yaml
# Pod에서 사용
spec:
  containers:
  - name: app
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secret
```

실무에서는 Secret을 YAML 파일에 직접 저장하지 않는다. Helm + `.Values`, ExternalSecrets Operator (AWS Secrets Manager 연동), Vault 등을 사용한다.

## NetworkPolicy - 파드 간 통신 제어

기본 상태의 K8s는 **모든 파드가 서로 자유롭게 통신 가능**하다. Namespace로 논리적으로 나눠도 네트워크 레벨에서는 막히지 않는다. 취약점이 있는 파드 하나(예: 오래된 라이브러리를 쓰는 프론트엔드)가 뚫리면, 같은 클러스터의 DB 파드에도 곧바로 접근할 수 있다는 뜻이다.

```yaml
# 1. 기본값: 네임스페이스 내 모든 인그레스 트래픽 차단 (default-deny)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: prod
spec:
  podSelector: {}      # 네임스페이스 내 모든 파드에 적용
  policyTypes:
  - Ingress
```

```yaml
# 2. 필요한 트래픽만 명시적으로 허용
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: postgres
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api-server     # api-server 라벨을 가진 파드만 DB 접근 허용
    ports:
    - protocol: TCP
      port: 5432
```

**주의**: NetworkPolicy는 CNI가 지원해야 실제로 동작한다. Flannel은 미지원, Calico/Cilium은 지원한다. "정책을 적용했는데 여전히 다 통신된다"는 문제의 원인은 대부분 CNI 미지원이다.

## etcd - 클러스터의 유일한 상태 저장소

etcd는 클러스터의 모든 상태(Pod, Deployment, Secret, ConfigMap...)가 저장되는 분산 Key-Value 저장소다. **API Server조차 etcd 없이는 아무것도 기억하지 못한다.** etcd가 완전히 사라지면 클러스터 전체가 사라진 것과 같다.

```
etcd 3대(홀수) 구성
- Raft 합의 알고리즘으로 과반수(quorum) 투표
- 3대 중 2대 이상 살아있으면 정상 동작
- 과반수가 죽으면 새로운 쓰기 합의 불가
```

**왜 홀수인가**: 짝수로 구성하면 네트워크 분할 시 정확히 반으로 나뉘어 과반수를 판단할 수 없는 상황이 생긴다. 3대는 1대 장애를 견디고, 5대는 2대 장애를 견딘다.

```bash
# 백업 (정기 크론으로 실행)
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot-$(date +%F).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 복구 (컨트롤플레인 중단 후 새 데이터 디렉터리로 restore)
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot-2026-04-01.db \
  --data-dir=/var/lib/etcd-restored
```

etcd 백업이 없으면, 컨트롤플레인이 통째로 날아갔을 때(디스크 손상, 오퍼레이터 실수) **워커 노드의 컨테이너는 계속 돌고 있어도 그 상태를 아는 시스템이 없어 새로운 배포·스케일링·복구가 전부 불가능**해진다. 정기 스냅샷 백업과 별도 스토리지 보관은 온프레미스 클러스터 운영의 필수 항목이다.

## StatefulSet vs Deployment

Deployment는 파드를 동일한 것으로 취급한다. 어떤 파드가 죽어도 이름이 바뀐 새 파드로 대체되면 그만이다. **DB, 메시지 큐 리더처럼 "정체성"과 "순서"가 중요한 워크로드에는 맞지 않다.**

| | Deployment | StatefulSet |
|---|---|---|
| 파드 이름 | 랜덤 해시 (app-7d9f8-x2j4k) | 고정 순번 (app-0, app-1, app-2) |
| 스토리지 | 파드 간 공유 또는 없음 | 파드별 고유 PVC (재시작해도 유지) |
| 시작/종료 순서 | 무작위 | 순차적 (0 → 1 → 2, 종료는 역순) |
| 네트워크 ID | Service 뒤에서 랜덤 | 고정 DNS (app-0.svc.namespace) |

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres              # headless service 필요
  replicas: 3
  podManagementPolicy: OrderedReady  # 기본값: 0번이 Ready 돼야 1번 시작
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 20Gi
```

`OrderedReady`는 이전 파드가 Ready 상태가 되어야 다음 파드를 시작한다. **Primary(app-0)가 먼저 뜨고 그다음 Replica들이 순서대로 붙어야 하는 DB 클러스터링**에 필요한 보장이다. 병렬로 전부 띄우고 싶으면 `podManagementPolicy: Parallel`을 쓰지만, 이 경우 순서 보장을 잃는다.

## 트러블슈팅 심화: CrashLoopBackOff / OOMKilled / Evicted

**CrashLoopBackOff**는 컨테이너가 반복해서 죽고 재시작될 때 뜬다. 원인은 크게 세 가지로 나뉜다.

```bash
kubectl logs <pod> --previous     # 죽기 직전 로그 확인이 1순위
kubectl describe pod <pod>        # Last State, Exit Code, Events 확인
```

| Exit Code | 의미 | 원인 예시 |
|---|---|---|
| 1 | 애플리케이션 에러 | 처리 안 된 예외, 설정 파일 누락 |
| 137 | SIGKILL (128+9) | OOMKilled, 또는 livenessProbe 실패로 강제 종료 |
| 143 | SIGTERM (128+15) | graceful shutdown 처리 중 timeout |
| 0 | 정상 종료인데 재시작 | 메인 프로세스가 즉시 끝나는 커맨드 설정 오류 |

**OOMKilled vs Evicted** - 둘 다 "메모리 문제로 파드가 사라졌다"지만 원인이 다르다.

```
OOMKilled
  컨테이너 하나가 자신의 memory limit을 초과
  → 커널 OOM Killer가 그 컨테이너 프로세스만 kill
  → kubectl describe pod에서 "Reason: OOMKilled" 확인
  → 대응: 해당 컨테이너의 memory limit 상향, 또는 메모리 릭 확인

Evicted
  노드 전체의 메모리/디스크가 압박 상태 (kubelet이 감지)
  → kubelet이 QoS 낮은 파드부터 강제 종료해서 노드를 지킴
  → kubectl describe pod에서 "Reason: Evicted", "The node was low on resource: memory" 확인
  → 대응: 노드의 다른 파드들 자원 사용량 점검, requests=limits로 Guaranteed QoS 부여
```

**QoS 클래스**가 Evicted 순서를 결정한다.

```
Guaranteed: request == limit   → 가장 나중에 축출
Burstable:  request < limit    → 중간
BestEffort: request/limit 미설정 → 가장 먼저 축출
```

노드가 메모리 압박 상태가 되면 kubelet은 BestEffort 파드부터 순서대로 제거한다. 중요 서비스는 Guaranteed QoS(request=limit)로 설정해야 이 순서에서 밀리지 않는다.

## 실무 운영 경험: 레플리카 10개+ 운영

기존에는 Pod를 고정 수로 운영했다. 트래픽이 적은 새벽에도 10개가 떠있었다.

개선 내용:

**1. HPA 도입**

```yaml
minReplicas: 2   # 최소 2개 (새벽)
maxReplicas: 12  # 최대 12개 (트래픽 피크)
```

피크 타임에는 자동으로 늘고, 새벽에는 2개로 줄어 인프라 비용 60% 절감.

**2. readinessProbe + PDB**

배포 중 트래픽 끊김 없도록 readinessProbe로 준비 완료 확인, PDB로 최소 2개 유지.

**3. Resource Limit 설정**

OOMKill이 간헐적으로 발생하던 문제를 Memory Limit을 적절히 올리고 Request를 맞춰 해결.

## 면접에서 자주 나오는 질문

**Q. HPA가 동작하지 않을 때 원인은?**

1. `resources.requests`가 설정되지 않음 (HPA는 request 기준으로 사용률 계산).
2. Metrics Server가 설치되지 않음.
3. `minReplicas`와 현재 Pod 수가 이미 동일.

**Q. readinessProbe와 livenessProbe를 다르게 설정하는 이유는?**

readinessProbe 실패 시 Service에서 제외되고, 자연히 로드밸런서 대상에서도 제외된다. 컨테이너는 살아있지만 트래픽만 안 받는다. livenessProbe 실패 시 컨테이너가 재시작된다. readinessProbe를 먼저 엄격하게 설정하면 livenessProbe가 불필요하게 재시작하는 것을 방지한다.

**Q. Pod가 Pending 상태일 때 원인은?**

1. 요청한 CPU/메모리를 가진 노드가 없음.
2. 노드에 taint가 있고 Pod에 toleration이 없음.
3. PVC가 바인딩되지 않음.
4. 이미지 Pull 실패.

`kubectl describe pod <name>`으로 Events 섹션에서 원인을 확인한다.

**Q. 무중단 배포를 위해 반드시 필요한 설정은?**

readinessProbe (준비 완료 전 트래픽 차단), `maxUnavailable: 0` (항상 desired 수 유지), preStop hook 또는 적절한 graceful shutdown (진행 중인 요청 처리 완료), 충분한 terminationGracePeriodSeconds.

**Q. HPA와 Cluster Autoscaler가 동시에 걸려있을 때 스케일 아웃 흐름은?**

HPA가 먼저 반응해서 replica 수를 늘리라고 지시한다. 스케줄러가 새 파드를 배치할 자리를 찾다가 기존 노드에 자원이 없으면 파드가 Pending 상태로 남는다. Cluster Autoscaler는 이 Pending 파드를 감지해서 노드를 추가한다. 파드 스케일링(초 단위)과 노드 스케일링(분 단위) 사이에 지연이 존재하고, 그 사이엔 일부 요청이 지연되거나 실패할 수 있다. 트래픽 급증이 예상되는 서비스는 이 지연을 감수하기보다 minReplicas를 여유 있게 잡거나, 예측 가능한 트래픽에는 cron 기반 사전 스케일 업을 병행한다.

**Q. etcd 쿼럼이 깨지면 클러스터에 어떤 일이 생기고 어떻게 복구하는가?**

etcd는 Raft로 과반수 투표를 하기 때문에, 과반수(3대 중 2대 등)가 죽으면 새로운 쓰기 합의를 할 수 없다. API Server로 리소스를 생성·수정하는 모든 요청이 실패한다. 이미 떠있는 워크로드는 즉시 죽지 않지만, 새 배포·스케일링·헬스체크 기반 재시작 판단이 전부 멈춘다. 복구는 살아있는 노드로 쿼럼을 다시 구성하거나, 정기적으로 떠둔 snapshot으로 새 etcd 클러스터를 restore한 뒤 컨트롤플레인을 다시 붙이는 방식이다. 백업이 없으면 클러스터 상태 자체를 잃는다.

**Q. StatefulSet이 순서를 보장하는 방식과 그게 필요한 실제 사례는?**

OrderedReady 정책 하에 파드가 0번부터 순차적으로 생성되고, 이전 파드가 Ready 상태여야 다음 파드가 생성된다. 종료는 역순이다. Primary/Replica 구조의 DB 클러스터(PostgreSQL, Kafka, Elasticsearch 등)에서 Primary가 먼저 살아있어야 Replica들이 정상적으로 복제를 시작할 수 있는 경우 필요하다. Deployment는 파드를 무작위로 재생성하기 때문에 이런 순서·정체성 보장을 할 수 없다.

**Q. OOMKilled와 Evicted를 구분하는 기준과 각각의 대응은?**

OOMKilled는 컨테이너 자신의 memory limit을 초과해서 커널 OOM Killer가 그 컨테이너만 강제 종료한 경우다. 해당 컨테이너의 limit을 올리거나 메모리 누수를 확인해야 한다. Evicted는 노드 전체의 자원이 부족해서 kubelet이 QoS가 낮은 파드부터 강제로 제거한 경우다. 노드 단위 자원 부족 문제이므로 다른 파드들의 자원 사용을 점검하고, 중요 파드는 request=limit(Guaranteed QoS)로 설정해 축출 순서에서 뒤로 밀리게 해야 한다.

**Q. NetworkPolicy가 하나도 없는 클러스터의 실제 보안 위험은?**

기본적으로 모든 파드가 네임스페이스 경계와 무관하게 서로 통신할 수 있다. 외부에서 취약점이 있는 파드 하나(예: 오래된 라이브러리를 쓰는 프론트엔드)를 장악하면, 같은 클러스터 안의 DB, 내부 API, Secret을 다루는 파드까지 네트워크 레벨에서 바로 접근이 가능해진다. NetworkPolicy로 default-deny를 걸고 필요한 통신만 명시적으로 허용해야 하나의 파드가 뚫려도 피해 범위(blast radius)를 제한할 수 있다. 단, Flannel처럼 NetworkPolicy를 지원하지 않는 CNI를 쓰면 정책을 적용해도 무시된다.
